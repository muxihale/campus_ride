# Техническая архитектура

## Согласованный стек

- Bun 1.4: менеджер пакетов, workspaces и среда исполнения приложений.
- Turborepo: запуск задач монорепозитория и локальный кэш сборок.
- React, TypeScript, Vite: отдельное клиентское приложение без необходимости SSR.
- Tailwind CSS и shadcn/ui с Base UI: общий пакет компонентов и тема пресета `b1tgce4mm`.
- NestJS: модульный REST API, валидация запросов и Swagger/OpenAPI.
- PostgreSQL 17 и Prisma ORM 7: хранение данных, миграции и типизированный клиент.
- Docker Compose: PostgreSQL и полный запуск для демонстрации.
- ESLint для React, Oxlint для API, Prettier для форматирования; Vitest и Supertest для API.

Конкретные версии зависимостей закреплены в `bun.lock`. Prisma CLI, клиент и PostgreSQL-адаптер закреплены на одной версии 7.10.1, чтобы не смешивать несовместимые основные версии.

## Структура и выполнение

`apps/web` содержит маршруты и экраны. `packages/ui` содержит общие компоненты, CSS-тему и утилиты. `apps/api` содержит HTTP-контроллеры, прикладные сервисы, проверки прав и доступ к БД. Браузер не обращается к PostgreSQL напрямую и не импортирует Prisma.

В разработке Vite принимает запросы на `http://localhost:5173` и проксирует `/api` в NestJS на `http://localhost:3001`. В Compose используется тот же URL браузера, а прокси направляет `/api` на внутренний адрес `http://api:3001`. Это позволяет использовать относительные URL в клиенте.

NestJS компилируется TypeScript-компилятором, затем собранный JavaScript исполняется Bun. В режиме разработки `nest start --watch --exec bun` сохраняет метаданные декораторов NestJS; прямой запуск исходного `main.ts` не является основной командой запуска.

Время в БД — UTC в `timestamptz`. Входная дата поиска, формы и отображение используют `Asia/Yekaterinburg` (UTC+5), независимо от часового пояса браузера или машины разработчика. Передача времени через API — ISO 8601 с часовым поясом. День поиска преобразуется сервером в полуоткрытый UTC-интервал.

## Модули API

Подготовлены `PrismaModule`, контроллер состояния и `AuthModule` с регистрацией, входом, выходом, созданием сессии и текущим пользователем. Остальные возможности ниже запланированы:

- `Auth`: смена пароля и отзыв остальных сессий; регистрация, вход, выход и текущий пользователь уже реализованы.
- `Users`: получение и частичное редактирование собственного профиля реализованы; подключение водителя с первым автомобилем реализовано; API списка, добавления и изменения своих автомобилей реализован; остальные настройки запланированы.
- `Locations`: реализованы публичные справочники районов, корпусов и точек маршрутов с поиском, фильтрами и пагинацией.
- `Rides`: реализованы создание, список и чтение своих поездок, редактирование и удаление черновиков с остановками; публикация с событием и уведомлением реализована; API публичного поиска и расчёт остатка мест реализованы; публичная карточка реализована; отмена реализована; API старта реализовано с атомарной обработкой PENDING, API завершения реализовано; интерфейсы старта и завершения реализованы.
- `Bookings`: реализовано создание PENDING с резервированием мест, фиксацией цены и идемпотентностью; подтверждение и отклонение водителем, API и интерфейсы заявок пассажира и водителя реализованы.
- `Payments`: исключительно имитация списания и полного возврата.
- `Reviews`: двусторонние отзывы, рейтинги и модерация.
- `Notifications`: реализованы собственный список с фильтрами и прочтение для всех ролей, уведомления о заявках и решениях водителя.
- `Activity`: личная история и административный аудит.
- `Admin`: административные сценарии через те же прикладные правила, без прямого обхода сервисов.

Контроллер принимает DTO и контекст пользователя; сервис проверяет бизнес-правила и проводит транзакцию. Клиент не управляет авторством, ролями, суммами, остатком мест и состоянием платежа.

## Аутентификация и доступ — целевой вариант

Пароли хешируются Argon2id; восстановление исходного пароля невозможно. Нормализованный email приводится к нижнему регистру и хранится уникально. Используются серверные сессии, а не токены в `localStorage`: случайный токен в `HttpOnly` cookie `campusride_session`, в таблице `Session` только его хеш и срок действия. Срок сессии — 7 дней.

Cookie имеет `SameSite=Lax`, `Path=/`, в HTTPS-развёртывании — `Secure`; для локального HTTP флаг `Secure` отключён. Изменяющие запросы проверяют разрешённый `Origin`, включая запросы входа; запросы без браузерного Origin допустимы только в явно определённых серверных/тестовых сценариях. CORS не заменяет авторизацию и CSRF-защиту.

Выход удаляет текущую сессию, блокировка пользователя отзывает все сессии. Смена пароля отзывает остальные. Guard проверяет сессию, состояние пользователя, роль и владение конкретным объектом. Вход и регистрация получают ограничение частоты запросов. Пароли, cookie, хеши токенов и полные строки подключения не попадают в журналы.

Реализованный подэтап: регистрация с нормализацией email и хешированием Argon2id, атомарное создание `User`/`UserRole`/`Session`, 256-битный случайный токен с SHA-256-хешем в БД, семидневная cookie и `SessionGuard` для `/auth/me`. Guard проверяет срок сессии и блокировку пользователя. Регистрация требует точного совпадения `Origin` с `WEB_ORIGIN`; лимит — 10 попыток с IP за 60 секунд через `@nestjs/throttler`. Лимиты локальны одному процессу; `trust proxy` не включён, клиентский `X-Forwarded-For` не определяет лимит. Интерактивная регистрация в Swagger выполняется через фронтенд-прокси.

Отзыв сессий при смене пароля/административной блокировке и проверка владения объектами ещё не реализованы. Наличие `SessionGuard` не означает готовность будущих предметных маршрутов.

## Транзакции

Сервис бронирования блокирует строку поездки через `SELECT … FOR UPDATE` внутри Prisma-транзакции, затем заново читает состояние и сумму занятых мест. Все операции, меняющие активные заявки этой поездки, используют тот же порядок блокировки. При операциях над несколькими поездками блокировки берутся в стабильном порядке по идентификатору.

На этапе создания заявки в транзакции записываются бронирование и начальное событие статуса. Решения водителя атомарно обновляют заявку и добавляют событие. Уведомления записываются в тех же транзакциях. Демонстрационные платежи, отмена заявки/поездки и полный возврат выполняются в этих же транзакциях. Старт и завершение также записывают статусы, уведомления и журнал в одной транзакции. Частичный уникальный индекс не допускает двух активных заявок одного пассажира на поездку. Идемпотентность команды проверяется независимо от клиентского состояния кнопки.

Проверки уровня БД (диапазон оценки, положительное количество мест, уникальность) дополняют прикладные проверки. При конфликте клиент получает безопасную ошибку, обновляет остаток и предлагает повторить действие.

## Инфраструктура и проверки

`GET /api/health` проверяет только доступность HTTP API. `GET /api/health/ready` выполняет запрос к PostgreSQL и возвращает `503`, если БД недоступна. Ответ `200` от первого маршрута не означает, что миграции, бронирования и сценарии предметной области готовы.

Prisma Client генерируется перед сборкой API и не хранится в Git. Начальная миграция находится в репозитории; новые изменения схемы проводятся отдельными миграциями. В Compose API ждёт PostgreSQL, применяет миграции и запускает сервер; фронтенд ждёт успешной проверки готовности API.

GitHub Actions на push/PR устанавливает зависимости из lockfile, генерирует Prisma Client, проверяет форматирование, линтинг, типы, HTTP-тесты, сборку и применение миграций к временному PostgreSQL. Наличие workflow не означает, что он уже выполнялся: без коммита и push удалённый запуск не произойдёт.

Docker-образы собраны локально, полный Compose-стек запущен и проверен: API соединяется с PostgreSQL напрямую и через прокси фронтенда. Для работы установлен Docker с Compose и Buildx через Homebrew. Среда контейнеров — отдельный профиль Colima `campusride` (4 CPU, 4 ГБ RAM), Docker context `colima-campusride`. PostgreSQL 17 и миграции проверены; SQL-проверки ограничений с откатом выполняются командой `bun run db:test`. Инструкция установки и переключения между контейнерным и локальным режимами находится в README.

Вход проверяет Argon2id-хеш; для неизвестного email выполняется проверка фиктивного хеша. Неверные учётные данные и блокировка возвращают одинаковый `401`. Успешный вход создаёт новую сессию; выход идемпотентно удаляет только текущую и очищает cookie с теми же параметрами. Вход имеет отдельный лимит 10 попыток с IP в минуту, включая невалидные формы. Вход и выход защищены проверкой Origin.

### Серверные роли

`@Roles("DRIVER")` на методе или контроллере подключает последовательно `SessionGuard` и `RolesGuard`. Роли берутся из БД при каждом запросе по действующей cookie-сессии, а не из заголовков или тела клиента. Без действующей сессии возвращается `401`, без подходящей роли — `403`. Декоратор принимает одну или несколько ролей: достаточно любой из них. Настройка метода заменяет настройку контроллера. `ADMIN` не получает неявный доступ к действиям водителя: для совместного доступа следует явно перечислить обе роли.

`AuthModule` экспортирует оба guard для будущих предметных модулей. `RolesGuard` без пользователя отклоняет запрос с `401`, без заданных ролей — с `403`. Декоратор требует хотя бы одну роль. Совмещение ролей поддерживается; назначение и отзыв роли учитываются без повторного входа. Проверку владения конкретной поездкой или заявкой необходимо добавлять в соответствующий прикладной сервис отдельно.

Проверки проходят на тестовом контроллере с настоящими сессиями и PostgreSQL: матрица трёх ролей, настройки контроллера/метода, совмещение и отзыв ролей, блокировка и отзыв сессии, подмена роли клиентом. Этот контроллер не подключён к рабочему приложению и не добавляет административных маршрутов в его Swagger.

### Профиль пользователя

`UsersModule` предоставляет `GET /me` и `PATCH /me` через `SessionGuard`; изменение дополнительно проверяет Origin. Идентификатор пользователя берётся из сессии. DTO разрешает только имя, телефон и принадлежность к университету, сервис явно перечисляет записываемые поля. Ответ выбирает безопасные поля Prisma, включая телефон и роли. Пароли, статусы и роли не меняются, действующие сессии сохраняются. Это собственный профиль, а не административный API редактирования пользователей.

### Подключение водителя

`POST /me/driver-profile` защищён ролью пассажира, сессией и Origin. В одной Prisma-транзакции создаются `DriverProfile`, вложенный `Vehicle` и роль `DRIVER` через upsert. Уникальные ключи профиля и нормализованного госномера предотвращают повторы, включая параллельные запросы. При конфликте вся транзакция откатывается. Остальные роли не удаляются, сессии не заменяются. DTO валидирует вложенный автомобиль и запрещает произвольные поля. Клиент получает безопасный обновлённый профиль и сразу обновляет меню кабинетов.

### Автомобили водителя

`VehiclesModule` предоставляет `GET/POST /me/vehicles` и `PATCH /me/vehicles/:id`. Доступ закрыт ролью `DRIVER`; на мутациях проверяется Origin. Список всегда ограничен `driverId` из сессии. Изменение использует единый запрос Prisma с условиями UUID и владельца: чужие и отсутствующие записи получают одинаковый `404`. DTO не допускают изменение владельца и прочих служебных полей.

Создание автомобиля и недостающего профиля подготовленного водителя выполняется в транзакции. `createMany` с `skipDuplicates` сохраняет существующее описание профиля и безопасно обрабатывает параллельное первое добавление. Уникальный нормализованный госномер защищён БД; конфликт возвращает `409` с откатом. Список и количество считываются в одной транзакции `RepeatableRead`, чтобы пагинация была согласованной. Поиск и четыре группы фильтров объединяются через «И». Экран управления автомобилями доступен водителю по hash-маршруту `#/vehicles`. Поиск и четыре фильтра передаются в API после подтверждения формы; пагинация — по 10 записей. Формы вызывают POST/PATCH, после сохранения список повторно читается из API. Устаревшие ответы игнорируются при изменении параметров или уходе со страницы. Ошибка сохранения не очищает введённые значения; ответ 401 возвращает форму входа.

### Справочники маршрутов

`LocationsModule` предоставляет публичные GET-маршруты районов, корпусов и точек без изменения данных. Каждый список поддерживает поиск и четыре фильтра. Для районов и корпусов фильтры по связанным точкам объединены внутри одного `some`, чтобы все условия выполнялись для одной точки. Данные и total читаются в транзакции `RepeatableRead`, сортировка стабилизирована UUID. DTO отклоняют неизвестные параметры и ограничивают размер страницы.

Повторяемый seed создаёт районы, корпуса и точки в одной транзакции с постоянными исходными UUID, сохраняя существующие значения. Данные и источники адресов описаны в [demo-data.md](demo-data.md). Миграция не требуется: используются существующие сущности `District`, `Campus`, `Location`.

### Черновик поездки

`RidesModule` предоставляет `POST /rides` с проверкой сессии, роли `DRIVER` и Origin. DTO принимает только разрешённые поля и валидирует вложенные остановки. Сервис проверяет собственный автомобиль и вместимость, существование всех точек, уникальность маршрута и будущее время с часовым поясом. Автор и `DRAFT` назначаются сервером. Черновик и упорядоченные остановки сохраняются в одной транзакции; ошибка не оставляет частичных данных. Цена — целые копейки в пределах PostgreSQL integer; нулевая цена допустима. Новая миграция не нужна: используются существующие `Ride` и `RideStop`.

### Управление своими черновиками

Приватные GET-маршруты `me/rides` и `me/rides/:id` ограничены водителем из сессии. Список поддерживает поиск и фильтры, сортировку и пагинацию; строки и total читаются в `RepeatableRead`. Публичная карточка и API поиска имеют отдельный безопасный контракт, описанный ниже.

PATCH/DELETE `rides/:id` проверяют роль и Origin. Сервис блокирует собственную строку через параметризованный `SELECT … FOR UPDATE`, затем проверяет `DRAFT` и отсутствие любых бронирований. PATCH объединяет текущие данные с запросом и использует общую с созданием бизнес-валидацию. У DTO частичного обновления нет значений по умолчанию, чтобы пропущенные флаги и остановки не сбрасывались. Замена остановок и запись выполняются в одной транзакции; параллельные изменения читают актуальные поля после блокировки. DELETE сохраняет чужие поездки и историю, возвращая конфликт для неподходящего статуса или связанных данных.

### Форма создания и редактирования поездки

Клиентские hash-маршруты `rides/new` и `rides/:id/edit` доступны в кабинете водителя. Форма загружает все страницы собственных автомобилей и точек, для редактирования — приватный `GET /me/rides/:id`. Другие статусы, кроме `DRAFT`, не показывают редактируемую форму. UUID вариантов берутся из API. Остановки можно добавлять, удалять и переставлять; в запрос отправляется только их порядок и locationId.

Время отображается через `Intl.DateTimeFormat` с `Asia/Yekaterinburg`, ввод преобразуется в ISO 8601 с `+05:00`, независимо от локального пояса браузера. Рубли разбираются как целая и дробная строковые части, затем складываются в целые копейки; лишние десятичные знаки и выход за PostgreSQL integer отклоняются. Клиент повторяет основные проверки для обратной связи, сервер остаётся источником проверки прав и бизнес-правил. Сохранение вызывает POST/PATCH и показывает подтверждение; экран списка и кнопка публикации доступны водителю.

### Публикация поездки

`POST /rides/:id/publish` работает в одной транзакции с блокировкой собственной строки `Ride FOR UPDATE`. `PUBLISHED` возвращается без побочных действий; для остальных состояний допускается только `DRAFT` без бронирований. Перед первым переходом DTO повторно валидирует сохранённые поля, общий валидатор проверяет время, маршрут, владельца автомобиля и вместимость. `Vehicle FOR SHARE` предотвращает изменение вместимости между проверкой и завершением публикации.

Обновление статуса, `RideStatusEvent` с автором и переходом DRAFT → PUBLISHED, и системное `Notification` владельцу записываются вместе. Ошибка любого шага откатывает всё. Строковая блокировка обеспечивает отсутствие дублей при конкурентных вызовах и повторах после потери ответа. Тест с реальной транзакцией искусственно прерывает шаг уведомления после предыдущих SQL-записей и проверяет полный откат. Существующих сущностей и `NotificationKind.SYSTEM` достаточно; миграция не требуется. Интерфейс публикации и список поездок реализованы на этапе 29.6.

### Список своих поездок

Hash-маршрут `#/rides` доступен роли `DRIVER`; кабинет водителя и форма сохранённого черновика содержат ссылки на него. Список читает `GET /me/rides` с поиском, фильтрами, сортировкой и пагинацией по 10 записей. Названия точек и данные своих автомобилей загружаются через общие клиентские типы и постраничный загрузчик. Смена фильтров не перечитывает справочники; после действия обновляются список и справочники. Устаревшие ответы игнорируются, при сокращении total страница возвращается в допустимый диапазон.

Подтверждение публикации вызывает POST `rides/:id/publish`, удаления — DELETE `rides/:id`; после успеха список загружается заново с прежними фильтрами. Действия черновика отображаются только для `DRAFT`, но права и переходы проверяет сервер. Копейки форматируются в рубли, все даты — в Екатеринбурге. В отличие от формы создания, временные фильтры допускают прошлые даты. Ошибки, отсутствие поездок и отсутствие совпадений представлены отдельно, ответ 401 возвращает вход. Форма публичного поиска, карточки результатов и экран деталей реализованы.

### Публичный поиск поездок

Отдельный `PublicSearchController` обслуживает GET `/rides` без сессии, не наследуя guard защищённых мутаций. Запрос всегда ограничен будущим `PUBLISHED`, активным аккаунтом и ролью водителя; неизвестные параметры запрещены. Ответ собирается явным Prisma select публичных полей: маршрут, цена, предложенные места, условия, имя водителя и описание автомобиля без госномера и контактов. Список и total читаются в `RepeatableRead`, сортировка стабилизирована UUID.

Календарные фильтры строят полуоткрытые UTC-границы из местной даты и часов UTC+5: timeTo включает всю минуту. Временные фильтры требуют дату, чтобы не подменять её локальным днём сервера. Публичный minSeats проверяет свободный остаток после агрегации PENDING/CONFIRMED; заполненные поездки исключаются. Интерфейс поиска и результатов реализован; API карточки описан ниже.

### Расчёт свободных мест

Публичный поиск выполняется параметризованным SQL через Prisma.sql. LATERAL-подзапрос суммирует seats только для PENDING/CONFIRMED по текущей поездке, используя существующий индекс Booking(rideId, status). CTE вычисляет availableSeats, ограничивая отрицательные значения нулём, и отбирает доступные поездки до LIMIT/OFFSET. Поиск не загружает все заявки или все подходящие UUID в память приложения.

Проекция явно перечисляет публичные скалярные поля и JSON-объекты маршрута, водителя и автомобиля. SQL-параметры используются для текста и фильтров; ORDER BY выбирается из фиксированных вариантов. Страница и total используют один предикат в RepeatableRead. Остаток не хранится отдельным изменяемым счётчиком, поэтому подтверждение заявки не списывает места второй раз. Новых сущностей и миграций не требуется; создание бронирований и решения водителя реализованы в BookingsModule.

### Публичная карточка поездки

GET `/rides/:id` использует общий с поиском построитель CTE доступности. Предикат UUID добавляется параметром, затем проверяются статус, будущее время, активность и роль водителя, положительный остаток. Закрытые записи и отсутствующий UUID неразличимы по ответу 404. Приватное чтение водителя `/me/rides/:id` не менялось.

Один SQL-запрос читает публичную проекцию, остаток, упорядоченные остановки и агрегат рейтинга. Явная проекция не содержит контактов, госномеров, хешей и сессий. Рейтинг строится по видимым отзывам фактических пассажиров завершённых бронирований и поездок, где пользователь был водителем; среднее округляется до двух знаков, отсутствие данных возвращает null. Индивидуальные отзывы и сведения о бронированиях в карточку не входят. Схема БД не менялась.

### Форма публичного поиска

App выделяет публичный hash-маршрут `#/search` до проверки роли кабинета: форма доступна гостю и пользователю любой роли, даже если восстановление сессии ещё не завершено. Применённые параметры находятся после `?` внутри hash и восстанавливают состояние формы при навигации истории и перезагрузке. Компонент пересоздаётся при смене hash, а завершения устаревших запросов игнорируются.

Районы и корпуса читаются через общий постраничный загрузчик. `search-form.ts` валидирует и сериализует фильтры, сохраняет false и нулевую цену, переводит рубли в целые копейки. Неизвестные или повторные параметры ссылки не запускают поиск автоматически. Отправка вызывает реальный публичный GET /rides; SearchResults отображает карточки из items, total и границы страниц из ответа API. Есть сброс, повтор ошибок и русские подписи времени Екатеринбурга. Дата не зависит от часового пояса устройства.

### Результаты публичного поиска

Карточки показывают адреса, время UTC+5, цену в рублях, водителя, автомобиль, условия и availableSeats отдельно от seatsTotal. Сортировка и пагинация меняют hash-параметры, сохраняя фильтры; новая сортировка и отправка формы сбрасывают страницу. Смена hash перемонтирует поиск, а очистка эффектов игнорирует устаревшие ответы. Загрузка, ошибка с повтором, отсутствие совпадений и пустая страница имеют отдельные состояния. Ссылка на экран деталей передаёт исходные параметры поиска в search; экран проверяет их перед построением ссылки возврата.

### Публичный экран карточки

`#/ride/<UUID>` открывает PublicRideScreen без требования сессии. Компонент читает GET /rides/:id и показывает точки маршрута по position, адреса, время Екатеринбурга, цену за место, свободный остаток, условия, автомобиль и публичный профиль водителя. Отсутствие рейтинга, описания и остановок имеет явные подписи. Ответы 400/404 дают состояние недоступности, сетевые и серверные ошибки — повтор загрузки. При переходе на другую карточку компонент перемонтируется; очистка эффекта игнорирует старый ответ. Параметр search содержит URL-параметры исходного поиска; возврат восстанавливает фильтры, сортировку и страницу и заново читает актуальные результаты. Некорректный параметр возврата заменяется маршрутом #/search. В карточку подключена форма бронирования BookingForm; API создания заявки реализовано отдельно.

### Создание заявки пассажира

BookingsModule предоставляет POST /rides/:id/bookings под SessionGuard, Roles(PASSENGER) и TrustedOriginGuard. DTO запрещает лишние поля; пассажир и цена назначаются сервером. Сервис блокирует Ride через FOR UPDATE в транзакции ReadCommitted, проверяет requestKey, перечитывает доступность и сумму мест PENDING/CONFIRMED. После ожидания блокировки время проверяется заново. Все будущие операции изменения резерва должны брать эту же блокировку перед записью Booking.

Повтор ключа для того же пассажира, поездки и seats возвращает прежнюю заявку с текущим статусом до проверки доступности, без повторной записи. Конфликт ключа или активной заявки даёт 409. Дополнительно действуют глобальная уникальность requestKey и частичный уникальный индекс активной заявки пассажира. Начальное BookingStatusEvent (null → PENDING) записывается вложенно в той же транзакции. Ответ содержит только собственную заявку; связанные профили и служебные данные не сериализуются. Конкурентные HTTP-тесты с настоящим PostgreSQL проверяют борьбу за места, одновременные повторы и разные ключи одного пассажира.

### Подтверждение и отклонение заявки

BookingDecisionsController предоставляет POST /bookings/:id/confirm и /reject под ролью DRIVER и проверкой Origin. BookingsService.decide выбирает поездку по заявке и driverId и блокирует только строку Ride через FOR UPDATE OF r, затем перечитывает Booking. Чужая и отсутствующая заявка дают одинаковый 404. Порядок блокировки совпадает с созданием; параллельные решения и новые заявки сериализуются по поездке.

Для нового решения проверяются PENDING, PUBLISHED и будущее время отправления. CONFIRMED сохраняет число зарезервированных мест; REJECTED исключается из суммы резерва. Изменение заявки и событие PENDING → целевой статус выполняются одной транзакцией. Причина отклонения нормализуется DTO и сохраняется в cancellationReason и BookingStatusEvent.reason. Повтор целевого статуса возвращает заявку без записи, но повтор REJECTED с другой причиной даёт 409. Уведомления записываются в транзакции решения; демо-платёж также меняется в этой транзакции. HTTP-тесты проверяют гонку противоположных решений, повторов и освобождения мест с новой заявкой.

### Форма бронирования

PublicRideScreen получает текущего пользователя и состояние восстановления сессии от App. BookingForm доступна роли PASSENGER для чужой поездки; серверные проверки остаются обязательными. Смена пользователя или маршрута перемонтирует форму. Гость переходит на #/login с returnTo, после успешного входа или регистрации App восстанавливает только внутренний маршрут карточки. Исходный параметр search сохраняется.

Выбор ограничен availableSeats, итог считается в целых копейках. POST отправляет только seats и requestKey. Ключ хранится в ref открытой формы: при неизвестном результате число мест блокируется, повтор использует тот же запрос. Синхронный busy-ref защищает от двойной отправки до React-рендера. После определённого отказа ключ сбрасывается; конфликты 404/409 вызывают перечитывание карточки. При уменьшении остатка выбор ограничивается заново. Успешная заявка отображает текущий статус и стоимость по серверной unitPriceKopecks.

Обновление свободных мест — отдельный GET карточки, без оптимистичного вычитания. Если после бронирования карточка становится недоступна (404), результат заявки сохраняется, выбор закрывается и показывается сообщение. Ошибка обновления также не превращает успешный POST в неудачу: доступен повтор только GET. Очистка эффекта игнорирует ответы после ухода; последовательность запросов обновления защищает от устаревших ответов. Список сохранённых заявок после перезагрузки доступен в кабинете пассажира.

### Собственные заявки пассажира

OwnBookingsController предоставляет GET /me/bookings под SessionGuard и ролью PASSENGER. OwnBookingsService всегда добавляет passengerId из сессии, применяет поиск и фильтры до пагинации и читает строки с total в RepeatableRead. Временная граница upcoming фиксируется один раз на запрос; history построена как NOT этого предиката, без пересечений. История не ограничивается публичной доступностью поездки. Выборка явно перечисляет безопасные поля связанных объектов; цена берётся из Booking, а не текущей Ride.

Hash-маршрут #/bookings доступен только пассажиру, ссылка добавлена в навигацию, кабинет пассажира и результат бронирования. BookingsScreen хранит черновик фильтров отдельно от применённого запроса. Смена фильтров сбрасывает страницу; переходы по страницам и обновление сохраняют применённые условия. При уменьшении total страница корректируется. Ключ результата и очистка эффекта исключают старые данные при смене запроса. Есть состояния загрузки, ошибки с повтором, пустого списка и отсутствия совпадений; 401 возвращает вход. Даты фильтров переводятся из Екатеринбурга, деньги — из рублей в целые копейки; старые даты разрешены. Закрытая публичная карточка не препятствует просмотру кратких данных своей заявки.

### Список заявок и решения в кабинете водителя

DriverBookingsController предоставляет GET /me/ride-bookings с ролью DRIVER. DriverBookingsService ограничивает ride.driverId пользователем сессии независимо от фильтров; дополнительный rideId не снимает это ограничение. Выборка явно перечисляет поля пассажира (id, fullName, affiliation), исключает requestKey и контакты. В RepeatableRead читаются строки, total и резерв PENDING/CONFIRMED связанных поездок. Внутренние массивы резерва не попадают в ответ; availableSeats вычисляется для каждой поездки.

BookingsScreen использует общий интерфейс фильтров и пагинации в двух режимах. Кабинет перемонтирует его при переключении роли просмотра, чтобы запросы и состояния не смешивались. Режим водителя #/ride-bookings читает отдельный endpoint и показывает пассажира и свободный остаток. Решения доступны для PENDING будущей PUBLISHED-поездки по времени последней загрузки; сервер повторяет проверку во время команды. Панель подтверждения действия требует причину для REJECTED. Busy-ref и disabled защищают от двойной отправки; ответ после ухода игнорируется. Успех обновляет список с прежними фильтрами, а 404/409 закрывает устаревшую команду и перечитывает данные. При временной ошибке команда и причина сохраняются для повтора.

### Уведомления о бронированиях и полный сценарий

BookingsService создаёт BOOKING_REQUEST водителю после записи заявки, а BOOKING_CONFIRMED/BOOKING_REJECTED — пассажиру после решения. Все записи используют исходную транзакцию и блокировку Ride. Ветки идемпотентного повтора возвращаются раньше уведомления. Тесты с PostgreSQL подменяют только шаг notification.create внутри настоящей транзакции и проверяют откат предыдущих SQL-записей.

NotificationsModule разрешает GET /notifications и PATCH /notifications/:id/read всем трём ролям. userId всегда из сессии. Фильтры применяются до пагинации; список и total читаются в RepeatableRead. Изменение требует Origin; updateMany с readAt=null и владельцем, затем чтение в транзакции сохраняют первую отметку при параллельных повторах. Чужие записи не раскрываются.

NotificationsScreen в #/notifications доступен из навигации всех кабинетов. Применённые фильтры отделены от черновика; запросы старого раздела игнорируются, страницы корректируются при сокращении total. Прочтение перечитывает список с прежними фильтрами. Ссылки разрешены только на известные внутренние разделы заявок и кабинета водителя. Центр обновляется при открытии и вручную, без фонового polling.

Полный HTTP-сценарий поиска, карточки, заявки, уведомления водителю, решения и предстоящей поездки пассажира работает на PostgreSQL. BookingFlow.test.tsx дополнительно проверяет навигацию, формы и смену ролей с моделью транспорта в тесте; это отдельная проверка интерфейса, не замена серверного сценария. Демо-платёж создаётся с заявкой и меняется вместе с подтверждением/отменой.

### Оплата, отмена и полный возврат

Вложенный Payment создаётся атомарно с Booking. changePayment проверяет isDemo, сумму по фиксированной цене заявки и допустимый переход. SUCCEEDED сохраняет paidAt, REFUNDED — refundedAt; прежние даты сохраняются. Каждый переход пишет ActivityLog и PAYMENT_UPDATED. Ранние ветки повторов команд не вызывают новых платежей или уведомлений. Поле amountKopecks расширено до bigint: 8 × Int32-максимум превышает integer, но помещается в безопасное целое JavaScript. serializePayment явно преобразует сумму в number перед JSON во всех ответах и списках.

Отмена пассажира блокирует Ride по владельцу Booking, проверяет статус/startedAt/будущее время после ожидания блокировки, затем cancelReservation меняет платёж, заявку, событие, историю и уведомление водителю. Отмена водителя блокирует свою Ride и последовательно отменяет все активные Booking в стабильном порядке UUID, затем меняет поездку и её событие. IN_PROGRESS/COMPLETED не отменяются. Повтор CANCELLED-заявки сохраняет первоначальную причину; повтор отмены поездки с другой причиной даёт конфликт. Административный маршрут добавляется позднее.

Миграция demo_payments заполняет отсутствующие платежи прежних заявок, не трогает существующие. CANCELLED с историческим CONFIRMED получает REFUNDED; без подтверждения — CANCELLED. Для CONFIRMED/COMPLETED фиксируется SUCCEEDED. Заполнение не имитирует новые уведомления. Отдельный тест применяет начальную и новую миграции в изолированной PostgreSQL-схеме, проверяет все старые статусы, сохранение платежа и переполнение, затем откатывает схему.

PaymentInfo отображает демонстрационный характер, сумму, статус и даты в результатах бронирования и списках. В BookingsScreen добавлена команда отмены с явным подтверждением и необязательной причиной, в RidesScreen — отмена поездки с обязательной причиной. Действия скрыты для неподходящих статусов, сервер повторно проверяет права и время. Ошибка неизвестного результата сохраняет причину для повтора; успех перечитывает список. Тесты проверяют гонки отмены с подтверждением/бронированием и полное восстановление уже обработанных заявок, если следующий возврат или уведомление не удалось.

### Старт поездки — этапы 02.1–02.2

RideStartController предоставляет POST /rides/:id/start под ролью DRIVER и TrustedOriginGuard. RideStartService блокирует собственную Ride в Prisma-транзакции и после блокировки проверяет статус и timestamps. Для PUBLISHED без startedAt/completedAt назначает серверное время, IN_PROGRESS и вложенное событие RideStatusEvent. Повтор начатой поездки с согласованными timestamps возвращает прежнее время. Ошибки скрыты за безопасным 503, нарушения предметных правил — 409.

До изменения Ride сервис выбирает все PENDING в порядке UUID. В той же транзакции changePayment отменяет неоплаченный демо-платёж, затем Booking меняется на REJECTED с фиксированной причиной и вложенным событием статуса. Все действия выполняются после получения общей блокировки Ride. Одновременный POST бронирования либо успевает создать PENDING и старт обрабатывает её, либо видит IN_PROGRESS и отклоняется. Гонка отмены и старта сохраняет только один допустимый переход. Подтверждённые заявки и платежи не меняются; уведомления сохраняются в общей транзакции. startedAt включён в приватные представления своих поездок; публичный контракт не расширяется.

HTTP-тесты с PostgreSQL проверяют повторы, права, будущую и просроченную поездку, запрет новых заявок/отмен, гонки команд и реальный откат транзакции после SQL-записи статуса и события.

Старт не использует отдельную транзакцию для каждой заявки и не вызывает HTTP-команду решения водителя: её временные ограничения отличаются от старта просроченной поездки. Общий changePayment сохраняет проверку суммы/isDemo, историю платежа и PAYMENT_UPDATED. Подтверждённые оплаты и исторические заявки не затрагиваются. Некорректный статус/сумма платежа прерывает весь переход с 409; ошибка записи после обработки первой заявки или после изменения Ride даёт 503 и откатывает все записи. Повтор IN_PROGRESS возвращается до обработки заявок. Тесты PostgreSQL проверяют несколько PENDING, нулевые суммы, сохранение CONFIRMED, повторы, гонки с подтверждением/отменой и оба места отказа транзакции. Уведомления о старте и автоотклонении сохраняются атомарно с переходом.

### Завершение поездки — этап 02.3

RideCompletionController предоставляет POST /rides/:id/complete под ролью DRIVER и проверкой Origin. RideCompletionService блокирует свою Ride тем же порядком, что старт, бронирование, решения и отмены. Проверяет IN_PROGRESS, timestamps и отсутствие PENDING; для каждого CONFIRMED проверяет существование успешного isDemo-платежа и сумму по фиксированной цене заявки. При неконсистентности возвращает 409 без исправлений данных молча.

CONFIRMED обрабатываются в порядке UUID: меняются на COMPLETED с вложенным событием статуса. Затем Ride становится COMPLETED с серверным completedAt и своим событием. Вся обработка — одна Prisma-транзакция. Payment не записывается повторно, возврат не выполняется, REJECTED/CANCELLED не затрагиваются. Корректный повтор COMPLETED возвращается до обработки заявок с прежними датами. Приватное представление Ride дополнено completedAt; публичный контракт не расширяется.

HTTP-тесты PostgreSQL покрывают несколько подтверждённых заявок, нулевые оплаты, сохранение истории/платежей, права, повторы, timestamps, гонку с недопустимой отменой и полный откат при сбое второй заявки либо после обновления Ride. Кнопки управления реализованы в 02.4; уведомления и ActivityLog завершения сохраняются атомарно с переходом.

### Управление жизненным циклом в кабинете водителя — 02.4

RidesScreen расширен командами start/complete с общей таблицей русских заголовков, предупреждений и результатов. Старт доступен PUBLISHED без timestamps, завершение — IN_PROGRESS с startedAt и без completedAt. Начало не ограничено запланированным временем, поскольку API допускает ручной старт. Фактические startedAt/completedAt показываются по Екатеринбургу из ответа списка, без оптимистичного назначения дат.

Любая команда требует явного подтверждения с маршрутом и отправлением. Busy-ref защищает от двойной отправки, фильтры и пагинация блокируются при открытой команде. После успеха список обновляется с прежними фильтрами/страницей. Временный сбой сохраняет команду start/complete для повтора; 404/409 закрывает её и перечитывает данные, 401 возвращает вход. Ошибка GET после успеха не повторяет POST. Очистка эффекта игнорирует завершившуюся команду после ухода из раздела. DOM-тесты проверяют подтверждение, даты, статусы, повтор, конфликты, сохранение фильтров, двойную отправку и уход во время запроса.

Уведомления жизненного цикла: RIDE_STARTED и RIDE_COMPLETED отправляются водителю (ссылка `#/rides`) и пассажирам подтверждённых заявок (ссылка `#/bookings`). Ранее отменённые и отклонённые заявки не получают этих уведомлений. При автоотклонении ожидающей заявки пассажир получает BOOKING_REJECTED с причиной начала поездки. Журнал сохраняет `ride.started`, `ride.completed`, `booking.rejected` (automatic=true) и `booking.completed` с автором-водителем, ресурсом и переходом статуса. Записи атомарны со статусами; последовательные и параллельные повторы не создают дублей. Сбой журнала или уведомления откатывает всю операцию.

## Двусторонние отзывы — 03.1

ReviewsModule предоставляет создание отзыва по завершённой заявке. Автор берётся из серверной сессии, получатель — из пары пассажир/водитель. Проверка роли привязана к стороне участия; административная роль не даёт права оценивать чужую поездку. Блокировка Ride сериализует запись с жизненным циклом и параллельными отзывами. Уникальность (bookingId, authorId) сохраняется после скрытия. Ответ содержит только поля отзыва. Уведомления и ActivityLog добавляются отдельно в 03.5.

## Списки отзывов и рейтинги — 03.2

ReviewListService использует параметризованные SQL-запросы с общим условием допустимого исторического участия. Роль получателя вычисляется по Ride.driverId и Booking.passengerId, а не по текущим UserRole. Скрытые отзывы, незавершённые участия и неверная пара участников исключаются. Публичные DTO не содержат bookingId; собственный список возвращает его для связи с поездкой. Контакты и причины модерации не выдаются. Фильтры применяются до пагинации; список и total читаются в RepeatableRead. Средние оценки округляются в PostgreSQL и возвращаются числами отдельно для водителя и пассажира. Рейтинг без отзывов — null с нулевым счётчиком.

## Форма отзыва пассажира — 03.3

В режиме пассажира BookingsScreen показывает BookingReview только при Booking=COMPLETED и Ride=COMPLETED. Компонент загружает собственный отправленный отзыв через GET /me/reviews с bookingId. Пока загрузка не завершена успешно, отправка недоступна. Для существующего отзыва показываются оценка, текст и время Екатеринбурга. Пустой результат открывает возможность оценить водителя; права повторно проверяет API.

Форма требует оценку и непустой комментарий, отправляет только rating и trim-комментарий, блокирует повторный POST до ответа. Сетевая ошибка/503 сохраняет ввод. При 404/409 форма закрывается и перечитывает отзыв: ранее принятая запись отображается, а при отсутствии видимой записи повторная отправка блокируется до обновления заявок. Так обрабатывается потерянный ответ и скрытый отзыв без раскрытия модерационных данных. 401 возвращает к входу; поздние ответы после ухода игнорируются. Комментарии рендерятся как текст. После успеха серверный ответ сохраняется в карточке без повторного POST и сброса фильтров списка.

## Форма отзыва водителя — 03.4

BookingReview — общая форма для обеих сторон. BookingsScreen в режиме водителя показывает её у завершённых заявок завершённой поездки с данными пассажира. Подписи и имя получателя соответствуют стороне участия, а POST по-прежнему содержит только rating/comment: получателя определяет сервер. Каждый пассажир оценивается по своей заявке; уже оставленная оценка загружается через direction=sent и bookingId. Ключ формы включает режим кабинета и заявку, чтобы локальное состояние не переносилось между ролями. Сохранены проверки, блокировка двойной отправки, безопасный повтор, обработка конфликта и игнорирование поздних ответов. Тесты общей формы выполняются для обеих ролей; отдельный сценарий проверяет независимые оценки двух пассажиров одной поездки.

## Экран отзывов, уведомления и аудит — 03.5

ReviewsScreen доступен всем трём ролям через меню кабинета и ссылку уведомления #/reviews. Показывает собственные полученные/оставленные отзывы, поиск по тексту и именам, фильтры роли получателя, оценки и дат, сортировку и пагинацию. Даты вводятся в часовом поясе Екатеринбурга. Два рейтинга аккаунта загружаются отдельно от фильтров списка и не меняют смысл при переключении на оставленные отзывы. Пустое состояние, ошибка с повтором и истечение сессии обрабатываются явно; поздние ответы после ухода игнорируются. Комментарии отображаются как текст. Карточка публичной поездки уже показывает рейтинг водителя и число подходящих нескрытых отзывов.

Создание отзыва дополняется уведомлением получателю и review.created в той же транзакции. Автор определяется серверной сессией, получатель и роль — участием. В журнале не дублируется текст комментария. Уникальность автора на заявку и блокировка поездки исключают повторные записи при конкурирующих запросах. Ошибка уведомления или журнала откатывает весь отзыв.

## Сквозная проверка отзывов — 03.6

Единый HTTP-тест проходит создание и публикацию поездки, поиск, бронь, подтверждение, старт, завершение и встречные отзывы в настоящем приложении с PostgreSQL. Проверяются отдельные рейтинги сторон, рейтинг в другой доступной карточке того же водителя, собственные списки, уведомления и review.created. До завершения отзыв запрещён; повтор, чужая и отклонённая заявка не создают дополнительных оценок и побочных записей. Интерфейсный ReviewFlow проходит обе сессии через App с подменой HTTP; он проверяет связность форм, меню, уведомлений, списков и рейтингов, а не доступность реальной БД. Ручная проверка адаптивности и сетевой активности описана в demo-lifecycle.md и не выдаётся за результат этих тестов.

## Административный список пользователей — 04.1

AdminModule использует общий AuthModule и PrismaModule. Контроллер GET /admin/users защищён Roles(ADMIN): сессия и актуальная роль проверяются до чтения списка. AdminUsersService строит параметризованные запросы Prisma с явным select разрешённых полей. Фильтр роли использует some по UserRole без размножения строк. Поиск и четыре вида фильтров применяются к items и total; оба запроса выполняются в одном снимке RepeatableRead. Сортировка имеет дополнительный ключ UUID. API не изменяет пользователей и не загружает секреты, сессии или телефон. Новая миграция не требуется.

## Блокировка аккаунтов — 04.2

UserStatusService использует существующие User.status, Session, ActivityLog и Notification; миграция не требуется. Причина хранится в журнале фактического перехода. Отмены поездок вынесены в общий cancelRide, заявки и платежи обрабатываются существующими cancelReservation/changePayment с автором-администратором. Административные уведомления явно отличаются от добровольной отмены участником.

Порядок блокировок: общий транзакционный advisory lock административных переходов (20261104, 42), SHARE пользователя-администратора с повторной проверкой роли, NO KEY UPDATE целевого аккаунта, все подходящие Ride по возрастанию UUID, затем Booking/Payment. NO KEY UPDATE совместим с KEY SHARE внешних ключей уведомлений, предотвращая цикл ожидания при записи уведомления участнику. До изменения Ride после ожидания повторно проверяются статус и даты. Прочие команды поездок/бронирований берут SHARE своего активного пользователя до Ride. Создание сессии при входе также берёт SHARE и повторно проверяет ACTIVE; блокировка либо удаляет уже созданную сессию, либо предотвращает её создание. Разблокировка не возрождает старые сессии.

Тесты HTTP с PostgreSQL проверяют обе роли одного аккаунта, несколько поездок и платежей, сохранение чужих участий и начатых/прошедших поездок, повторные и параллельные команды, гонки с бронированием, подтверждением и стартом. Отдельная проверка приостанавливает создание заявки/поездки после проверки сессии и возобновляет после блокировки. Сбои записи уведомления и журнала проверяются после обновления статуса и удаления сессий, чтобы подтвердить полный откат.

## Управление пользователями в интерфейсе — 04.3

AdminUsersScreen доступен роли ADMIN по #/admin и #/admin/users; ссылка «Пользователи» показывается в меню только администратору. Экран использует API списка и команды блокировки/разблокировки. Поддерживает поиск, роль, статус, принадлежность, диапазон регистрации, сортировку и страницы. Даты вводятся в часовом поясе Екатеринбурга. Локальные фильтры применяются явной кнопкой; после мутации сохраняются запрос и страница, а при уменьшении выдачи выбирается существующая последняя страница.

Панель подтверждения показывает пользователя и последствия, требует причину 1–500 символов. Фокус переводится на заголовок подтверждения; на время команды блокируются фильтры, пагинация и остальные действия. Собственный аккаунт не имеет кнопки изменения блокировки. Сервер остаётся источником проверки прав. Успех показывает реальные счётчики отмен/сессий и перечитывает список; changed=false объясняется как уже установленный статус. Ошибка загрузки после успеха повторяет только GET. Сетевые ошибки и 503 сохраняют причину для повтора; 404/409 закрывают устаревшее подтверждение и обновляют данные. 401 возвращает к входу, 403 скрывает данные и команды до повторной проверки доступа. Поздние ответы после ухода игнорируются.

## API модерации отзывов — 04.4

AdminReviewsService читает все отзывы с явным набором полей, включая скрытые и исключённые из публичного рейтинга. Роль получателя вычисляется по участию; некорректная пара обозначается null. Поиск и фильтры параметризованы, список и счётчик выполняются в RepeatableRead. Новая миграция не требуется: hiddenAt и hiddenReason уже есть в Review.

Для мутации берётся SHARE активного администратора и повторно проверяется ADMIN, затем блокируется строка Review. Команды не удаляют отзыв и не меняют оценку/комментарий; уникальность автора на заявку сохраняется. Скрытие/восстановление, аудит и уведомления атомарны; параллельные одинаковые команды дают ровно один фактический переход. Причина восстановления хранится в ActivityLog, а hiddenReason очищается. Отдельного счётчика рейтингов нет: все запросы рейтинга и публичной карточки уже исключают hiddenAt, поэтому результат обновляется сразу после коммита без фонового пересчёта. Тесты PostgreSQL проверяют обе роли, публичную карточку, повторную оценку, фильтры, права, повторы и откат при сбоях уведомления/журнала.

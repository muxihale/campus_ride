# Проверка бронирования в двух сессиях — 06.2

6 ноября 2026 года сценарий пройден в браузере с настоящими Vite, NestJS и PostgreSQL. Профили Default и Incognito имеют независимые cookie: водитель Михаил Кузнецов и пассажир Анна Соколова. HTTP не подменялся.

## Подготовка и повторение

1. Запустить приложение по README. В одном профиле войти водителем, в другом — пассажиром. Две вкладки одного профиля используют общую сессию и для этого не подходят.
2. Подготовить опубликованную поездку: метро «Уралмаш» → Мира, 19, 9 ноября 2026, 08:30 Екатеринбурга, 3 места по 150 ₽. Для поиска добавить в условия уникальную пометку. В этой проверке подготовка поездки выполнена через API водителя; создание через форму относится к отдельному сценарию жизненного цикла.
3. Пассажир: найти поездку по пометке, дате, интервалу 08:00–09:00, цене до 150 ₽ и минимум двум местам. Открыть «Подробнее».
4. Выбрать 2 места, нажать «Забронировать места». Ожидаются сообщение об ожидании водителя, сумма 300 ₽ и остаток 1 из 3. Открыть «Мои заявки».
5. Водитель: открыть уведомления, затем связанный раздел новой заявки. Найти нужную заявку, нажать «Подтвердить» и «Подтвердить заявку» в форме подтверждения.
6. Пассажир: открыть уведомления. Найти подтверждение заявки и демонстрационную оплату 300 ₽; перейти в связанный раздел. Выбрать «Предстоящие поездки», применить фильтры. Заявка должна быть подтверждена, демо-платёж — оплачен.

## Фактический результат

Все шаги от поиска до предстоящей заявки выполнены через интерфейс. Созданная заявка получила PENDING, затем CONFIRMED; платёж изменился с PENDING на SUCCEEDED, amountKopecks = 30000. Доступное число мест осталось 1 после подтверждения: повторного резервирования не произошло. У водителя появилось уведомление BOOKING_REQUEST, у пассажира — подтверждение и демо-оплата.

Наблюдались реальные сетевые запросы:

| Действие                      | Запрос                                                                                          | Ответ                                                                      |
| ----------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Поиск по условиям             | GET /api/rides?q=…&date=2026-11-09&timeFrom=08:00&timeTo=09:00&maxPriceKopecks=15000&minSeats=2 | 200                                                                        |
| Карточка и обновление остатка | GET /api/rides/:id                                                                              | 200                                                                        |
| Заявка на два места           | POST /api/rides/:id/bookings                                                                    | 201                                                                        |
| Решение водителя              | POST /api/bookings/:id/confirm                                                                  | Успешное подтверждение через интерфейс; CONFIRMED проверен последующим GET |
| Список водителя               | GET /api/me/ride-bookings?rideId=:id                                                            | 200                                                                        |
| Уведомления пассажира         | GET /api/notifications                                                                          | 200                                                                        |
| Предстоящие заявки            | GET /api/me/bookings?period=upcoming&sort=departureAsc&page=1&pageSize=10                       | 200                                                                        |

Для защиты откройте DevTools → Network → Fetch/XHR в обоих профилях до начала прохода, включите Preserve log. Покажите тело POST бронирования (seats и requestKey), результат, POST подтверждения и последующий GET предстоящих. Не экспортируйте cookie и заголовки сессии в публичные материалы.

## Регрессионная проверка

Повторно прошли существующие тесты:

- `bun run --filter @campusride/web test src/BookingFlow.test.tsx` — связность интерфейса с подменой HTTP.
- `bun run --filter @campusride/api test test/bookings.e2e-spec.ts -t 'полный сценарий: поиск'` — единый сценарий настоящего HTTP и PostgreSQL.

Ошибок основного сценария не обнаружено; изменения бизнес-логики не потребовались. В локальной базе обнаружены старые тестовые записи справочников, поэтому для репетиции следует использовать проверенные seed-точки по UUID либо чистую демонстрационную базу. Seed сохраняет существующие записи и сам их не удаляет. Подготовка окончательного набора данных относится к 06.6.

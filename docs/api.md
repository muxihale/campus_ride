# Контракт API

Базовый префикс: `/api`. Формат данных — JSON. Время — ISO 8601 с часовым поясом, идентификаторы — UUID, деньги — целые копейки. Данные об авторе и суммах сервер берёт из сессии и БД.

## Что реализовано сейчас

- `GET /health` — `{ "status": "ok", "service": "campusride-api" }`, без обращения к БД.
- `GET /health/ready` — дополнительно `"database": "connected"` при успешном `SELECT 1`; иначе `503`.
- `GET /docs` — Swagger UI.
- `GET /docs-json` — машиночитаемый OpenAPI.
- `POST /auth/register` — `{ email, password, fullName, affiliation? }`; создаёт пассажира и сессию, возвращает `201` и `{ id, email, fullName, affiliation, roles }`. Email приводится к нижнему регистру, пробелы по краям email/имени удаляются; пароль не обрезается. Роль всегда `PASSENGER`, неизвестные поля запрещены.
- `POST /auth/login` — `{ email, password }`; создаёт новую семидневную сессию, возвращает `200` и безопасные данные пользователя. Неверные учётные данные и заблокированный аккаунт дают одинаковый `401`, неверные/лишние поля — `400`. Лимит — 10 попыток с IP за 60 секунд, независимо от регистрации, включая невалидные формы.
- `POST /auth/logout` — удаляет только текущую сессию и очищает cookie, `204`; повторный выход, отсутствующая или истёкшая сессия также успешны.
- `GET /auth/me` — те же безопасные данные по cookie `campusride_session`, `200`; при отсутствующей, неверной, истёкшей или удалённой сессии и блокировке пользователя — `401`.

- `GET /me` — собственный профиль `{ id, email, fullName, phone, affiliation, roles }` по действующей сессии, `200`. Ответ не содержит паролей, хешей и данных сессии.
- `PATCH /me` — частичное изменение `{ fullName?, phone?, affiliation? }`, возвращает обновлённый профиль, `200`. Требует разрешённый `Origin`. Пропущенные поля сохраняются; имя обрезается по краям и должно содержать 2–100 символов, `null` для имени запрещён. Телефон — до 32 символов, цифры, пробелы, скобки, дефисы и необязательный `+` в начале; принадлежность — до 200 символов. Для телефона и принадлежности `null` и пустая строка после обрезки очищают значение. Неизвестные поля, включая `id`, `userId`, `email`, `password`, `status` и `roles`, запрещены (`400`); неверный Origin — `403`; нет активной сессии — `401`; недоступность БД — `503`. Выбрать чужого пользователя через этот маршрут нельзя: идентификатор берётся только из серверной сессии.

- `POST /me/driver-profile` — `{ bio?, vehicle: { make, model, color, registrationNumber, passengerSeats } }`; требует действующую сессию с ролью `PASSENGER` и разрешённый Origin. В одной транзакции создаёт профиль водителя, первый автомобиль и роль `DRIVER`, сохраняя остальные роли и сессии. Возвращает `201` и обновлённый профиль пользователя в формате `GET /me`. Повторное подключение или занятый госномер — `409`, без частичного сохранения. Неверные/лишние поля (включая вложенные) — `400`, нет роли пассажира или чужой Origin — `403`, нет активной сессии — `401`, сбой БД — `503`.

Описание водителя необязательно, до 1000 символов. Марка и модель — 1–60, цвет — 1–40 символов после обрезки пробелов. Пассажирских мест — целое число 1–8, без водителя. Поддерживается стандартный госномер легкового автомобиля РФ вида `А123ВС196`: пробелы удаляются, буквы приводятся к верхнему регистру и латинским соответствиям (`A123BC196`). Это обеспечивает единую уникальность для кириллицы и латиницы. `userId`, `driverId`, `id`, роли и другие служебные поля не принимаются.

- `GET /me/vehicles` — только свои автомобили с поиском, фильтрами и пагинацией; требуется роль `DRIVER`. Параметры: `q` (до 100 символов, поиск по марке, модели, цвету и нормализованному госномеру), `make`, `model`, `color` (по подстроке без учёта регистра), `minSeats` и `maxSeats` (1–8). Поиск и фильтры объединяются через «И». `page` — 1–1 000 000, по умолчанию 1; `pageSize` — 1–100, по умолчанию 20. Ответ `{ items, total, page, pageSize }`; сортировка по времени создания от новых к старым, затем по UUID для стабильной пагинации.
- `POST /me/vehicles` — добавляет автомобиль `{ make, model, color, registrationNumber, passengerSeats }` текущему водителю, возвращает `201` и автомобиль. Если у подготовленного аккаунта `DRIVER` нет профиля водителя, пустой профиль создаётся в той же транзакции; роли и существующее описание не меняются.
- `PATCH /me/vehicles/:id` — частично меняет перечисленные поля своего автомобиля, возвращает `200` и автомобиль. Пропущенные поля сохраняются; `null` запрещён. Чужой и отсутствующий UUID одинаково возвращают `404`.

Объект автомобиля содержит только `id`, `make`, `model`, `color`, `registrationNumber`, `passengerSeats`, `createdAt`. Мутации автомобилей требуют разрешённый Origin; все маршруты требуют активную сессию и роль `DRIVER`. Валидация и нормализация совпадают с первым автомобилем при подключении водителя: марка/модель 1–60, цвет 1–40, стандартный госномер легкового автомобиля РФ, 1–8 пассажирских мест. Занятый нормализованный номер даёт `409` без частичного сохранения. Лишние поля и параметры, неверный UUID или диапазон мест — `400`, нет сессии — `401`, нет роли/чужой Origin — `403`, сбой БД — `503`. `driverId` нельзя передать для изменения владельца или выбора чужого списка.

- `GET /districts` — публичный список районов/микрорайонов: поиск `q` по названию; фильтры `kind`, `address`, `locationName`, `campusId` по связанной точке.
- `GET /campuses` — публичный список корпусов УрФУ: поиск `q` по названию; фильтры `kind`, `address`, `locationName`, `districtId` по связанной точке.
- `GET /locations` — публичный список точек маршрутов: поиск `q` по названию или адресу; четыре фильтра `districtId`, `campusId`, `kind`, `address`.

Справочники возвращают `{ items, total, page, pageSize }`. Район и корпус содержат `{ id, name }`; точка — `{ id, name, address, kind, districtId, campusId, district: { id, name }, campus: { id, name } | null }`. `campusId` может быть `null` для точек вне кампуса. Списки без фильтров включают районы и корпуса без точек. Связанные фильтры применяются к одной точке, а не к разным точкам одного корпуса/района.

Поиск и текстовые фильтры — подстрока без учёта регистра, условия объединяются через «И». `kind` — `CAMPUS`, `MEETING_POINT` или `TRANSIT_STOP`; идентификаторы — UUID. `q` и `locationName` — до 100 символов, `address` — до 200; `page` — 1–1 000 000 (по умолчанию 1), `pageSize` — 1–100 (по умолчанию 20). Сортировка по названию, затем UUID. Неверные и лишние параметры дают `400`, неизвестный корректный UUID — пустой список `200`, недоступная БД — безопасный `503`. Сессия для чтения справочников не требуется; публичных маршрутов изменения нет.

- `POST /rides` — создание полностью заполненного черновика, `201`. Требует активную сессию с ролью `DRIVER` и разрешённый `Origin`. Тело: `{ vehicleId, originId, destinationId, departureAt, seatsTotal, priceKopecks, conditions, musicAllowed?, luggageAllowed?, smokingAllowed?, stops? }`. Музыка по умолчанию разрешена, багаж и курение — нет; остановки по умолчанию `[]`. `conditions` — обязательный текст условий и уточнения места встречи, 1–1000 символов после обрезки пробелов.

Создание проверяет принадлежность автомобиля водителю (чужой и отсутствующий — одинаковый `404`), наличие всех точек и отсутствие повторов в маршруте, включая остановки и конечные точки. `seatsTotal` — целое 1–8 и не больше вместимости автомобиля. Цена за место — целые копейки 0–2 147 483 647, включая бесплатные поездки. Время — строгая ISO 8601 дата с `T` и явным часовым поясом (`Z` или `+05:00`), обязательно в будущем; ответ нормализован в UTC.

Допускается до 10 промежуточных остановок `{ locationId }` в порядке посещения; позиции 1, 2, … назначает сервер. Черновик и остановки создаются в одной транзакции. Автор берётся только из сессии, статус всегда `DRAFT`; `driverId`, `status`, `id`, `availableSeats`, клиентские позиции остановок и другие лишние поля запрещены. Ошибки валидации и бизнес-условий — `400`, нет сессии/блокировка — `401`, нет роли/неразрешённый Origin — `403`, недоступность БД — безопасный `503`.

Ответ создания содержит `id`, `driverId`, поля запроса с настройками по умолчанию, `status`, `createdAt`, `updatedAt` и `stops: [{ id, locationId, position }]`. Он не содержит аккаунт, пароли, сессии или бронирования. Создание не публикует поездку; повторный корректный POST создаёт отдельный черновик. При публикации время и вместимость проверяются повторно.

- `GET /me/rides` — список только своих поездок всех статусов, включая прошлые. Ответ `{ items: RideDto[], total, page, pageSize }`. Поиск `q` (до 100 символов) по условиям, названиям/адресам конечных точек и марке/модели автомобиля без учёта регистра. Фильтры: `status`, `vehicleId`, `originId`, `destinationId`, `maxPriceKopecks`, `minSeats`, `departureFrom`, `departureTo`; все объединяются через «И». `minSeats` — предложенное число мест 1–8, не свободный остаток. Временные границы включительные, ISO 8601 с явным часовым поясом; обратный диапазон запрещён. `page` — 1–1 000 000 (по умолчанию 1), `pageSize` — 1–100 (20). `sort` — `departureAsc` (по умолчанию), `departureDesc`, `createdDesc`, затем UUID для стабильности.
- `GET /me/rides/:id` — безопасное представление своей поездки в формате ответа создания. Чужой и отсутствующий UUID дают одинаковый `404`. Это приватное чтение владельца; публичная карточка `GET /rides/:id` имеет отдельный безопасный контракт ниже.
- `PATCH /rides/:id` — частичное изменение только своего `DRAFT` без бронирований, возвращает `200` и обновлённую поездку. Принимает те же редактируемые поля, что создание; пропущенные значения сохраняются, `null` запрещён. Все бизнес-проверки выполняются повторно по объединённым старым и новым данным, включая вместимость и будущее время. Остановки заменяются целиком только при передаче `stops`; `[]` очищает их.
- `DELETE /rides/:id` — удаление только своего `DRAFT` без бронирований, `204` без тела. Остановки удаляются вместе с черновиком. Повторное удаление даёт `404`; связанные данные, препятствующие удалению, дают `409`.

Все маршруты своих поездок требуют сессию и роль `DRIVER`; PATCH/DELETE дополнительно требуют разрешённый Origin. Неверные поля/параметры/UUID — `400`, нет сессии — `401`, нет роли или чужой Origin — `403`, чужая/отсутствующая поездка — `404`, неподходящий статус или любое связанное бронирование — `409`, сбой БД — безопасный `503`. Ответы имеют `Cache-Control: no-store`. Изменение и удаление блокируют строку поездки в транзакции, чтобы проверка статуса, бронирований и замена остановок не расходились с записью; параллельные частичные изменения объединяются последовательно.

- `POST /rides/:id/publish` — публикация своего полностью заполненного черновика, `200` и актуальный `RideDto`. Тело отсутствует или `{}`; произвольные поля запрещены. Требует сессию, роль `DRIVER` и разрешённый Origin. Для `DRAFT` повторно проверяются заполненность полей, будущая дата, собственный автомобиль и его текущая вместимость, точки и порядок маршрута; бронирования у черновика запрещены.

Переход `DRAFT → PUBLISHED`, событие `RideStatusEvent` (автор, прежний и новый статусы) и одно уведомление владельцу сохраняются в одной транзакции. Уведомление: `kind=SYSTEM`, `resourceType=ride`, `resourceId=<UUID поездки>`, ссылка `#/driver`. Сохранённая запись доступна владельцу через GET /notifications и центр уведомлений.

Повтор `PUBLISHED` возвращает текущее состояние без изменения `updatedAt`, повторных событий или уведомлений, даже если время отправления уже прошло. Авторизация и проверка владельца действуют и при повторе. Параллельные команды сериализуются блокировкой строки поездки; данные автомобиля блокируются на чтение при первичной публикации. Ошибка события или уведомления откатывает статус целиком. Другие статусы и бронирования у черновика — `409`, чужая/отсутствующая поездка либо собственный автомобиль — `404`, незаполненные/невалидные условия или UUID — `400`, нет сессии — `401`, нет роли/чужой Origin — `403`, сбой БД — безопасный `503`. Успешный ответ имеет `Cache-Control: no-store`.

- `GET /rides` — публичный поиск без сессии, `200` и `{ items, total, page, pageSize }`. Выдаются только `PUBLISHED` с отправлением строго в будущем, активным аккаунтом водителя и сохранённой ролью `DRIVER`. Параметры статуса, автора и другие служебные фильтры не принимаются.

Поиск `q` (до 100 символов) работает по условиям, названиям и адресам конечных точек, их районам и корпусам без учёта регистра. Фильтры объединяются через «И»: `direction=TO_CAMPUS|FROM_CAMPUS`, `originDistrictId`, `campusId`, `date=YYYY-MM-DD`, `timeFrom=HH:mm`, `timeTo=HH:mm`, `maxPriceKopecks`, `minSeats`, `musicAllowed`, `luggageAllowed`, `smokingAllowed`. UUID должны быть корректны; неизвестный корректный UUID даёт пустой список. Булевы query-параметры принимают только `true`/`false`.

`TO_CAMPUS` означает связанную с корпусом точку назначения, `FROM_CAMPUS` — точку отправления. При направлении `campusId` применяется к соответствующему концу маршрута; без направления — к любому концу. `originDistrictId` всегда относится к точке отправления. Дата и время относятся к Екатеринбургу (UTC+5), а не к календарному дню UTC. Время требует `date`: начало включительно, конец включает всю указанную минуту; без времени выбираются сутки от местной полуночи до следующей полуночи, не включая её. Обратный временной диапазон запрещён.

`availableSeats` — `max(0, seatsTotal − сумма seats бронирований PENDING/CONFIRMED)`. Учитывается число мест, а не количество заявок. `CANCELLED`, `REJECTED`, `COMPLETED` не занимают места. Подтверждение PENDING → CONFIRMED не меняет остаток; отмена освобождает места. Без бронирований остаток равен предложенному числу мест. `minSeats` (1–8) применяется к свободному остатку; без параметра требуется хотя бы одно свободное место. Заполненные поездки и данные с превышением вместимости не выдаются. Цена — целые копейки 0–2 147 483 647.

`page` — 1–1 000 000 (по умолчанию 1), `pageSize` — 1–100 (20). Сортировка `departureAsc` (по умолчанию), `departureDesc`, `priceAsc`, `priceDesc`, с устойчивым дополнительным порядком по времени/UUID. Публичный элемент содержит `id`, `origin` и `destination` (`id/name/address`), `departureAt` в UTC, `seatsTotal`, `availableSeats`, цену, условия и три флага; водитель — только `id/fullName`, автомобиль — только `make/model/color`. Контакты, госномер, хеши, сессии и бронирования не возвращаются. Неверные/лишние параметры — `400`, сбой БД — безопасный `503`; ответ не кэшируется (`no-store`).

- `GET /rides/:id` — публичная карточка без сессии, `200`. Доступность совпадает с поиском: только будущая `PUBLISHED`, активный водитель с ролью DRIVER и положительный `availableSeats`. Черновая, прошедшая, заполненная, закрытая поездка и неизвестный UUID дают одинаковый `404` с сообщением «Поездка недоступна». Неверный UUID — `400`, сбой БД — безопасный `503`; успешный ответ имеет `Cache-Control: no-store`.

Карточка расширяет публичный элемент поиска: добавляет `status=PUBLISHED`, `stops: [{ position, location: { id, name, address } }]` в порядке посещения, `vehicle.passengerSeats`, `driver.bio`, `driver.rating` и `driver.reviewCount`. Начальная и конечная точки также содержат название и адрес. Остаток мест вычисляется тем же SQL-выражением по PENDING/CONFIRMED, что в поиске. Контакты, госномер, аккаунт, сессии, заявки и тексты отзывов не выдаются.

Рейтинг водителя — среднее rating видимых (`hiddenAt=null`) отзывов пассажиров, округлённое до двух десятичных знаков. Автор должен совпадать с пассажиром бронирования, получатель — с водителем соответствующей завершённой поездки; бронирование также должно иметь статус COMPLETED. Оценки пользователю в роли пассажира, скрытые отзывы и записи от посторонних авторов не учитываются. Без подходящих отзывов `rating=null`, `reviewCount=0`. API создания отзывов будет добавлен отдельно; карточка читает существующие данные. Все части ответа вычисляются в одном SQL-запросе из согласованного снимка БД.

Регистрация требует `Origin`, точно совпадающий с `WEB_ORIGIN` (`403` при несовпадении/отсутствии), принимает максимум 10 попыток с одного IP за 60 секунд (`429`, заголовок `Retry-After`). Валидация полей возвращает `400`, повторный email — `409`. Создание аккаунта, роли и сессии атомарно; при параллельных запросах одинакового нормализованного email создаётся только один аккаунт.

Токен — 32 случайных байта; в БД хранится SHA-256-хеш, в cookie — исходный токен. Пароль хешируется Argon2id. Cookie: `HttpOnly`, `SameSite=Lax`, `Path=/`, срок 7 дней, `Secure` при `NODE_ENV=production`. Токен, его хеш и пароль/хеш пароля не возвращаются в JSON. Успешные ответы маршрутов авторизации и профиля имеют `Cache-Control: no-store`.

Для работы с регистрацией из Swagger открывайте <http://localhost:5173/api/docs>, чтобы браузер отправлял разрешённый Origin. CLI-клиент указывает `Origin` явно и сохраняет cookie. Вход и выход также требуют точного совпадения Origin с WEB_ORIGIN.

Маршруты ниже — целевой контракт. Они ещё не реализованы и не должны появляться в Swagger как работающие до реализации.

## Правила целевых маршрутов

Списки принимают `q`, `page` (от 1), `pageSize` (по умолчанию 20, максимум 100) и разрешённую сортировку `sort`. Ответ: `{ items, total, page, pageSize }`. Фильтры определены в [спецификации](specification.md#10-поиск-и-фильтры). Параметры разных фильтров объединяются через «И».

Ошибки используют стандартный безопасный ответ NestJS: `{ statusCode, message, error }`; `message` может быть массивом ошибок полей. Для конфликтов бронирования прикладной ответ дополнительно содержит стабильный `code`, например `INSUFFICIENT_SEATS`, и `availableSeats`, если это уместно. Stack trace и данные подключения не возвращаются.

- `400`: неверные поля или параметры.
- `401`: нет действующей сессии.
- `403`: роль или состояние пользователя не разрешает действие.
- `404`: объект не существует или закрыт от текущего пользователя.
- `409`: недостаточно мест, повторное активное бронирование, изменённый идемпотентный запрос или недопустимый переход.
- `429`: превышена частота запросов.

Мутации не принимают произвольный статус через общий `PATCH`: для переходов используются отдельные команды. Повтор успешно выполненной статусной команды возвращает текущее представление без повторных побочных действий.

## Вход, профиль и настройки

- `PUT /me/password` — `{ currentPassword, newPassword }`; меняет пароль, отзывает остальные сессии, `204`.
- `GET /me/activity` — собственная история с поиском и фильтрами.

Минимальная длина пароля — 10, максимальная — 128 символов; имя — 2–100, телефон — до 32, принадлежность — до 200, описание условий — до 1000. Пустые строки нормализуются; пароли не обрезаются и не возвращаются в ответах.

## Поездки

- Список заявок водителя реализован как `GET /me/ride-bookings?rideId=<UUID>`; см. отдельный раздел ниже. Административный доступ добавляется отдельно.
- `GET /me/driver-statistics` — завершённые поездки, перевезённые места, демо-выручка, рейтинг; параметры периода.

Пример уже реализованного `POST /rides` (остальные маршруты раздела пока целевые):

```json
{
  "vehicleId": "<UUID автомобиля>",
  "originId": "<UUID места встречи>",
  "destinationId": "<UUID корпуса>",
  "departureAt": "2026-11-09T08:00:00+05:00",
  "seatsTotal": 3,
  "priceKopecks": 15000,

  "luggageAllowed": true,
```

Вместо текстовых заглушек передаются существующие UUID. Каждый элемент `stops` содержит `locationId`; порядок элементов определяет порядок остановок. Создание не принимает `driverId` или `status` от клиента.

Поиск поддерживает `direction=TO_CAMPUS|FROM_CAMPUS`, `originDistrictId`, `campusId`, `date=YYYY-MM-DD`, `timeFrom=HH:mm`, `timeTo=HH:mm`, `maxPriceKopecks`, `minSeats`, `luggageAllowed`, `musicAllowed`. Дата и часы относятся к Екатеринбургу. Для собственных поездок дополнительно доступен `status`. Публичный поиск ограничен `PUBLISHED`, будущим отправлением и положительным свободным остатком; контракт описан выше.

## Создание заявки — реализовано

`POST /rides/:id/bookings` требует действующую сессию с ролью PASSENGER и разрешённый Origin. Тело: `{ "seats": 1, "requestKey": "<UUID>" }`; seats — целое число 1–8, без преобразования строк. Все остальные поля запрещены. Сервер назначает passengerId, PENDING и цену за место из поездки. Поездка должна быть PUBLISHED, будущей, с активным водителем, сохранившим роль DRIVER. Собственную поездку бронировать нельзя.

Ответ `201`: `{ id, rideId, passengerId, requestKey, seats, unitPriceKopecks, status, createdAt }`. Даты — ISO 8601, цена — целые копейки. Бронирование и начальное событие статуса создаются атомарно. PENDING и CONFIRMED занимают места; остальные статусы не учитываются. Уведомление BOOKING_REQUEST водителю создаётся в той же транзакции. Вложенный payment содержит ожидающий демонстрационный платёж.

Повтор с тем же ключом, пользователем, поездкой и числом мест возвращает `200` с текущим состоянием той же заявки даже после изменения доступности поездки. Повтор не создаёт новый резерв или событие. UUID сравниваются без учёта регистра. Ключ нельзя использовать для другого набора параметров. Новая заявка после CANCELLED/REJECTED требует нового ключа.

Ошибки: `400` — неверный UUID/тело; `401` — недействующая сессия или заблокированный пассажир; `403` — нет роли PASSENGER, неверный/отсутствующий Origin или своя поездка; `404` — отсутствующая или недоступная поездка; `409` — нехватка мест, активная заявка или конфликт requestKey; `503` — безопасная ошибка БД. Ответы: Cache-Control: no-store.

## Решения водителя — реализовано

- `POST /bookings/:id/confirm` — пустое тело или `{}`. Переход PENDING → CONFIRMED сохраняет резерв мест.
- `POST /bookings/:id/reject` — `{ "reason": "Изменился маршрут" }`. Переход PENDING → REJECTED освобождает резерв. Причина — строка 1–500 символов после trim; сохраняется в cancellationReason и событии статуса.

Оба маршрута требуют сессию, роль DRIVER, владение поездкой и разрешённый Origin. Новое решение возможно только для PENDING и будущей PUBLISHED-поездки. Ответ `200`: поля BookingDto из создания заявки плюс `cancellationReason: string | null`. Цена и число мест не меняются. Переход и BookingStatusEvent с actorId водителя записываются в одной транзакции; уведомление пассажиру сохраняется в той же транзакции; платёж переводится в SUCCEEDED при подтверждении или CANCELLED при отклонении в той же транзакции.

Повтор того же решения возвращает текущую заявку без нового события даже после изменения статуса поездки. Повторное отклонение требует ту же нормализованную причину, иначе `409`. Противоположное решение или CANCELLED/COMPLETED не допускаются. Подтверждённую заявку отдельно отклонить нельзя.

Ошибки: `400` — неверный UUID, причина или лишние поля; `401` — недействующая сессия/блокировка; `403` — нет роли DRIVER или неверный/отсутствующий Origin; `404` — чужая либо отсутствующая заявка; `409` — недопустимый переход, поездка или конфликт причины; `503` — безопасная ошибка БД. Ответы: Cache-Control: no-store. Все операции с резервом блокируют строку поездки до чтения и записи заявки.

## Список заявок пассажира — реализовано

`GET /me/bookings` требует сессию и роль PASSENGER. Ограничение passengerId всегда берётся из сессии; передать чужой ID фильтром нельзя. Возвращаются все собственные заявки, включая завершённые, отклонённые и заявки закрытых поездок. Ответ: `{ items: OwnBookingDto[], total, page, pageSize }`. Элемент содержит поля ответа решения водителя и `ride: { id, status, departureAt, origin: { id, name, address }, destination: { id, name, address }, driver: { id, fullName }, vehicle: { make, model, color } }`. Цена unitPriceKopecks берётся из заявки, сумма равна seats × unitPriceKopecks. Контакты, госномер, аккаунт и сессии водителя не выдаются.

Поиск `q` — до 100 символов, без учёта регистра, по названиям/адресам маршрута, имени водителя, марке/модели автомобиля и причине отказа. Фильтры объединяются через И:

- `status` — BookingStatus; `rideStatus` — RideStatus.
- `period=all|upcoming|history` (all по умолчанию). Upcoming — PENDING/CONFIRMED при PUBLISHED и будущем отправлении; history — точное дополнение, включая отказы будущих поездок.
- `minSeats` — 1–8, число мест в заявке; `maxPriceKopecks` — 0–2147483647, зафиксированная цена одного места.
- `departureFrom`, `departureTo` — включительные ISO 8601 с часовым поясом; прошлые даты допустимы, обратный диапазон запрещён.

`sort=departureAsc|departureDesc|createdDesc` (departureAsc по умолчанию), затем UUID. `page` — 1–1000000 (1), `pageSize` — 1–100 (20). Total считается до пагинации в одном RepeatableRead-снимке со строками; пустая страница сохраняет total. Ошибки: 400 — неверные/лишние параметры, 401 — сессия или блокировка, 403 — нет роли, 503 — безопасная ошибка БД. Cache-Control: no-store. GET не требует Origin и не меняет данные.

## Список заявок водителя — реализовано

`GET /me/ride-bookings` требует сессию и роль DRIVER. Сервер всегда ограничивает выборку ride.driverId из сессии; администратор без роли DRIVER доступа не имеет. Поддерживает параметры GET /me/bookings и дополнительный `rideId` (UUID). Чужой либо отсутствующий rideId возвращает пустой список. Поиск q дополнительно проверяет имя и принадлежность пассажира к университету. Фильтры объединяются через И, сортировка и пагинация выполняются до выдачи в RepeatableRead вместе с total.

Ответ `{ items, total, page, pageSize }`: элемент аналогичен собственной заявке пассажира, но без requestKey; дополнен `passenger: { id, fullName, affiliation }` и `ride.availableSeats`. Остаток — max(0, seatsTotal − сумма seats PENDING/CONFIRMED) в том же снимке. Контакты, email, госномер, сессии и ключ повторной отправки не выдаются. Список содержит все статусы своих поездок, включая историю. Новых прав на решения маршрут не даёт: POST confirm/reject повторно проверяют владение и статус.

Ошибки: 400 — неверные/лишние параметры, 401 — недействующая сессия или блокировка, 403 — нет роли DRIVER, 503 — безопасная ошибка БД. Cache-Control: no-store. GET не требует Origin.

Объект бронирования содержит статус, число мест, зафиксированную цену за место, сумму, платёж и краткую поездку. Отдельного публичного маршрута, позволяющего клиенту выставить `SUCCEEDED`/`REFUNDED`, нет.

## Согласованность остатка в поиске

Агрегация активных бронирований и фильтр по остатку выполняются в PostgreSQL до сортировки и LIMIT/OFFSET. `total` учитывает тот же отбор. Записи страницы и количество читаются в одной транзакции RepeatableRead: конкурентная заявка не приводит к разным снимкам данных внутри ответа. Поиск не создаёт резерв; бронирование добавляется отдельным сценарием с повторной проверкой остатка. Сведения о пассажирах и заявках в публичный ответ не входят. В личном списке водителя `minSeats` по-прежнему относится к предложенному числу мест; новая семантика касается публичного GET /rides.

## Уведомления — реализовано

GET `/notifications` доступен всем трём ролям с действующей сессией, возвращает только записи текущего пользователя. Ответ `{ items: NotificationDto[], total, page, pageSize }`; элемент содержит id, kind, title, body, link, resourceType, resourceId, readAt (null до прочтения), createdAt. userId не выдаётся. Сортировка: createdAt DESC, UUID ASC; строки и total читаются в RepeatableRead.

Поиск q (до 100 символов) — по заголовку и тексту без учёта регистра. Фильтры через И: kind (NotificationKind), read=true|false, resourceType=booking|ride|payment|review|user, dateFrom/dateTo (включительные ISO 8601 с поясом). Обратный диапазон запрещён. page — 1–1000000 (1), pageSize — 1–100 (20). Лишние параметры запрещены.

PATCH `/notifications/:id/read` требует разрешённый Origin, принимает пустое тело или {} и возвращает 200 с NotificationDto. Меняет только свою запись; чужой/отсутствующий UUID — одинаковый 404. Повтор, включая параллельный, сохраняет первый readAt. Клиент не назначает дату прочтения. Массовое прочтение пока остаётся целевым маршрутом.

Создание PENDING записывает BOOKING_REQUEST водителю; решение — BOOKING_CONFIRMED или BOOKING_REJECTED пассажиру, с причиной отклонения. resourceType=booking, resourceId — UUID заявки; link — #/ride-bookings или #/bookings. Запись уведомления атомарна с заявкой/решением и событием статуса; при ошибке всё откатывается. Идемпотентные повторы не создают дублей. Публикация поездки сохраняет существующее SYSTEM-уведомление водителю.

Ошибки: 400 — неверные параметры/UUID/тело, 401 — сессия или блокировка, 403 — роль либо Origin изменения, 404 — чужая/отсутствующая запись при PATCH, 503 — безопасный сбой БД. Cache-Control: no-store. Новые события загружаются открытием раздела или кнопкой обновления; push-доставки нет.

## Демо-платежи, отмена и возврат — реализовано

BookingDto (в том числе создание, повтор, решения и списки обеих ролей) дополнен `payment: { id, amountKopecks, status, isDemo, paidAt, refundedAt } | null`. Сумма — seats × зафиксированная unitPriceKopecks, максимум 17179869176 копеек. BigInt PostgreSQL сериализуется в безопасное целое JSON. Для данных, созданных через API, payment существует; null допускается для диагностического чтения неконсистентных старых записей. Создание PENDING создаёт payment.PENDING; подтверждение автоматически имитирует оплату SUCCEEDED и сохраняет paidAt, отклонение переводит PENDING в CANCELLED. Нулевая сумма обрабатывается теми же переходами. Реальные деньги и внешние платёжные ключи не используются; публичного метода выставить статус платежа нет.

POST `/bookings/:id/cancel` — сессия PASSENGER, свой booking и разрешённый Origin. Пустое тело, {} или `{ reason?: string }`; причина 1–500 символов после trim, null/пустая строка и лишние поля запрещены. Только PENDING/CONFIRMED будущей PUBLISHED-поездки без startedAt. Результат 200 BookingDecisionDto с CANCELLED: PENDING-платёж отменяется без списания, SUCCEEDED полностью возвращается (REFUNDED и refundedAt). Повтор CANCELLED возвращает исходный результат, не меняет причину/даты даже после отправления. Другой конечный статус — 409; чужой/отсутствующий booking — одинаковый 404.

POST `/rides/:id/cancel` — сессия DRIVER, своя поездка и разрешённый Origin; обязательное `{ reason: string }`, 1–500 символов после trim. Только DRAFT/PUBLISHED без startedAt, включая просроченную PUBLISHED. Возвращает 200 `{ id, status: "CANCELLED", cancellationReason }`; причина также доступна в своих GET /me/rides и /me/rides/:id. В одной транзакции отменяет все PENDING/CONFIRMED, отменяет/возвращает платежи, сохраняет события RideStatusEvent/BookingStatusEvent, ActivityLog и уведомления. Повтор с прежней причиной идемпотентен, с другой — 409. IN_PROGRESS/COMPLETED — 409. Административная отмена остаётся отдельным будущим маршрутом.

Обе команды блокируют Ride перед работой с Booking/Payment. Гонки с подтверждением или новым бронированием не создают лишний резерв/повторный возврат. При сбое любого шага откатывается вся транзакция. Дополнительно к уведомлению об отмене создаются PAYMENT_UPDATED, а в ActivityLog фиксируются payment.succeeded/cancelled/refunded, booking.cancelled, ride.cancelled. Для повторов новые события и уведомления не создаются.

Ошибки: 400 — UUID/тело/причина, 401 — сессия/блокировка, 403 — роль/Origin, 404 — чужой/отсутствующий объект, 409 — статус/время/состояние платежа, 503 — безопасная ошибка БД. Cache-Control: no-store. Частичные возвраты не поддерживаются.

## Ручной старт поездки — 02.1–02.2 реализовано

POST `/rides/:id/start` требует сессию с ролью DRIVER, владение поездкой и разрешённый Origin. Тело отсутствует или {}; клиент не задаёт status/startedAt. Только PUBLISHED без startedAt/completedAt; будущее или прошедшее время отправления допускается, поскольку команда ручная. Ответ 200 `{ id, status: "IN_PROGRESS", startedAt: ISO8601 }`, Cache-Control: no-store. В своих GET /me/rides и /me/rides/:id добавлено startedAt (null до начала).

Команда блокирует Ride тем же FOR UPDATE, что создание/решения/отмена заявок. Статус, серверное время и RideStatusEvent PUBLISHED → IN_PROGRESS записываются в одной транзакции. Повтор IN_PROGRESS сохраняет startedAt и не создаёт событие. Неконсистентные timestamps не исправляются молча. После старта публичная карточка даёт 404, новые бронирования не принимаются; повтор уже созданной заявки по requestKey сохраняет свою идемпотентную семантику. Подтверждённые заявки и успешные платежи не меняются.

При старте все PENDING обрабатываются по UUID в одной транзакции с поездкой. Каждая заявка получает REJECTED, cancellationReason «Поездка началась без подтверждения заявки водителем.» и BookingStatusEvent PENDING → REJECTED с actorId водителя и той же причиной. Соответствующий PENDING-платёж переходит в CANCELLED без paidAt/refundedAt; места перестают входить в резерв. CONFIRMED и успешная оплата не меняются, как и ранее отклонённые/отменённые заявки. При некорректном платеже — 409 без частичных изменений. При сбое записи/уведомления — безопасный 503 с полным откатом ранее обработанных заявок и статуса поездки. Повторы не создают новых событий, логов или уведомлений платежа.

Общий механизм changePayment сохраняет PAYMENT_UPDATED и ActivityLog payment.cancelled. UI управления реализован в кабинете водителя; уведомления о старте/автоотклонении и ActivityLog старта сохраняются в той же транзакции. События RideStatusEvent и BookingStatusEvent уже сохраняются. Новая заявка в гонке либо создаётся до старта и отклоняется им, либо получает 404 после старта. Повтор её requestKey возвращает актуальное состояние без нового резерва.

Ошибки: 400 — UUID/лишние поля, 401 — сессия/блокировка, 403 — роль/Origin, 404 — чужая или отсутствующая поездка (одинаково), 409 — статус, timestamps либо некорректный платёж, 503 — безопасный сбой БД. Повтор после COMPLETED/CANCELLED — 409.

## Завершение поездки — 02.3 реализовано

POST `/rides/:id/complete` требует сессию с ролью DRIVER, владение поездкой и разрешённый Origin. Тело отсутствует или {}; клиент не задаёт статусы или timestamps. Только IN_PROGRESS с заданным startedAt, пустым completedAt и временем начала не позже серверного времени завершения. Ответ 200 `{ id, status: "COMPLETED", startedAt, completedAt }`, даты ISO 8601, Cache-Control: no-store. completedAt (null до завершения) добавлено в свои GET /me/rides и /me/rides/:id.

После блокировки Ride через FOR UPDATE сервис перечитывает состояние. Неожиданный PENDING у начатой поездки — конфликт; каждый CONFIRMED должен иметь успешный демо-платёж с корректной суммой. Все CONFIRMED становятся COMPLETED в порядке UUID, создаются BookingStatusEvent CONFIRMED → COMPLETED с actorId водителя. Затем записываются Ride.COMPLETED, серверный completedAt и RideStatusEvent IN_PROGRESS → COMPLETED. Всё выполняется одной транзакцией. Успешные Payment не обновляются: суммы, paidAt и updatedAt сохраняются. Исторические REJECTED/CANCELLED и их причины не меняются. Нулевые оплаты обрабатываются так же.

Повтор корректного COMPLETED возвращает прежние timestamps без событий. После завершения нельзя заново начать поездку, создать новую заявку или оформить обычную отмену/возврат. Закрытая поездка доступна в собственных списках, включая историю пассажира. UI управления реализован в кабинете водителя; уведомления и ActivityLog завершения сохраняются в той же транзакции, события статусов уже записываются.

Ошибки: 400 — UUID/лишние поля, 401 — сессия/блокировка, 403 — роль/Origin, 404 — чужая или отсутствующая поездка одинаково, 409 — статус, timestamps, неожиданный PENDING или некорректный платёж, 503 — безопасная ошибка БД с полным откатом. Параллельные повторы не дублируют события; сбой обработки второй заявки либо после SQL-обновления поездки откатывает все статусы и completedAt.

Уведомления жизненного цикла: RIDE_STARTED и RIDE_COMPLETED отправляются водителю (ссылка `#/rides`) и пассажирам подтверждённых заявок (ссылка `#/bookings`). Ранее отменённые и отклонённые заявки не получают этих уведомлений. При автоотклонении ожидающей заявки пассажир получает BOOKING_REJECTED с причиной начала поездки. Журнал сохраняет `ride.started`, `ride.completed`, `booking.rejected` (automatic=true) и `booking.completed` с автором-водителем, ресурсом и переходом статуса. Записи атомарны со статусами; последовательные и параллельные повторы не создают дублей. Сбой журнала или уведомления откатывает всю операцию.

## Создание двусторонних отзывов — 03.1

POST `/bookings/:id/reviews` реализован. Требует сессии, разрешённого Origin и роли PASSENGER для пассажира заявки либо DRIVER для водителя поездки. Тело: `{ "rating": 5, "comment": "Водитель приехал вовремя." }`. Оценка — целое число 1–5, комментарий — строка 1–1000 символов после trim. Неизвестные поля запрещены. Автор берётся из сессии, получатель определяется сервером по заявке.

Нужны Booking=COMPLETED и Ride=COMPLETED с непустыми корректными startedAt/completedAt; завершение не может быть в будущем. Чужая или отсутствующая заявка — одинаковый 404. Самооценка, незавершённое участие и повторный отзыв — 409. Скрытый отзыв также занимает единственную оценку автора; встречные отзывы независимы.

Ответ 201: `{ id, bookingId, authorId, recipientId, rating, comment, createdAt }`, без полей модерации и приватных данных пользователя; Cache-Control: no-store. Повтор с прежним текстом также даёт 409. Неверный UUID/тело — 400, нет сессии или аккаунт заблокирован — 401, нет роли или неверный Origin — 403, сбой БД — безопасный 503.

Транзакция блокирует Ride в том же порядке, что команды жизненного цикла, проверяет завершение и создаёт отзыв. Уникальный индекс (bookingId, authorId) дополнительно защищает от дублей. Параллельные запросы одного автора дают один 201 и один 409. Новая миграция не нужна: Review и ограничения оценки/комментария существуют в исходной схеме. Списки, UI, рейтинги, журнал и уведомления относятся к следующим этапам 03.2–03.5.

## Списки отзывов и раздельные рейтинги — 03.2

- GET `/me/reviews` — сессия любой из трёх ролей, только собственные полученные отзывы; `direction=sent` переключает на оставленные. Администратор видит только свои отзывы. Ответ `{ items, total, page, pageSize }`; элемент содержит id, bookingId, rating, comment, createdAt, author/recipient `{ id, fullName }` и recipientRole.
- GET `/users/:id/reviews` — публичный список полученных отзывов активного пользователя. Те же поля, кроме bookingId. Отсутствующий и заблокированный пользователь дают одинаковый 404.
- GET `/users/:id/ratings` — публичные раздельные оценки активного пользователя: `{ driver: { average, count }, passenger: { average, count } }`. Среднее округляется до двух знаков; без оценок average=null, count=0. Рейтинг считается по всем подходящим отзывам, независимо от фильтров списка.

Оба списка поддерживают q (комментарий и имена участников), recipientRole=DRIVER/PASSENGER, ratingMin/ratingMax (1–5), dateFrom/dateTo (ISO с часовым поясом, границы включительно), page (1–1000000), pageSize (1–100, по умолчанию 20), sort=newest/oldest. Все фильтры объединяются через И. Поиск регистронезависимый; символы `%` и `_` ищутся буквально. Роль фильтра — роль получателя в конкретной поездке, включая отправленный отзыв. Сортировка по createdAt и UUID обеспечивает стабильные страницы. Обратные диапазоны, неизвестные параметры и неверные значения дают 400. Публичный список не принимает direction.

Скрытые отзывы исключаются из обоих списков и рейтингов. Учитываются только завершённые заявки завершённых поездок с корректной парой автор/получатель; самооценки и посторонние участники исключены. Текущая смена роли пользователя не меняет историческую роль оценки. Контакты, платёжные данные и поля модерации не выдаются. Список и total читаются в одном снимке RepeatableRead. Ответы имеют Cache-Control: no-store; сбой БД — безопасный 503. Без сессии GET /me/reviews возвращает 401. UI добавляется на следующих этапах.

Для формы отзыва по конкретной заявке GET `/me/reviews` также принимает `bookingId=<UUID>`. Он объединяется с direction и остальными условиями через И и не расширяет доступ: возвращаются только собственные отзывы. Чужая либо отсутствующая заявка даёт пустой список. Неверный UUID — 400; публичный список не принимает bookingId. Это позволяет показать оставленную оценку без загрузки всей истории отзывов.

## Уведомления и аудит отзывов — 03.5

POST `/bookings/:id/reviews` атомарно создаёт Review, ActivityLog `review.created` и уведомление REVIEW_RECEIVED получателю. Журнал содержит автора, UUID отзыва, bookingId, recipientId, recipientRole и оценку, без копии комментария. Уведомление содержит роль оценки, число баллов, resourceType=review, resourceId отзыва и ссылку `#/reviews`. Повторный отзыв даёт 409 без новых уведомлений или записей журнала. Сбой любого шага откатывает отзыв и его вклад в рейтинг; ответ — безопасный 503.

## Список пользователей администратора — 04.1

GET `/admin/users` реализован; только сессия активного пользователя с ролью ADMIN. Нет сессии, она истекла или аккаунт заблокирован — 401, нет ADMIN — 403. Сервер проверяет актуальные роли, поэтому удаление ADMIN прекращает доступ без повторного входа.

Параметры: q (имя или email, до 100 символов), role=PASSENGER/DRIVER/ADMIN, status=ACTIVE/BLOCKED, affiliation (часть принадлежности к университету, до 200 символов), registeredFrom/registeredTo (ISO с часовым поясом, границы включительно), sort=createdDesc/createdAsc/nameAsc, page (1–1000000) и pageSize (1–100, по умолчанию 20). По умолчанию новые регистрации первыми. Поиск регистронезависимый, пробелы по краям удаляются, `%` и `_` ищутся буквально. Фильтры объединяются через И; роль означает наличие роли у пользователя и не создаёт дублей при нескольких ролях. При совпадении сортируемого значения используется UUID по возрастанию. Неизвестные/неверные параметры и обратный диапазон регистрации — 400.

Ответ 200 `{ items, total, page, pageSize }`. Поля пользователя: id, email, fullName, affiliation, status, roles, createdAt, updatedAt. Пароль, сессии, токены, телефон и связанные поездки не выдаются. Страница за пределами выдачи возвращает пустой items с актуальным total. Список и счётчик читаются в RepeatableRead, Cache-Control: no-store. Сбой БД — безопасный 503 без частичного списка. Блокировка и разблокировка реализованы в 04.2, интерфейс управления — в 04.3.

## Блокировка и разблокировка пользователей — 04.2

POST `/admin/users/:id/block` и `/admin/users/:id/unblock` требуют активную сессию ADMIN и разрешённый Origin. Тело `{ "reason": "Нарушение правил поездок" }`: обязательная строка 1–500 символов после trim, лишние поля запрещены. Нельзя изменить блокировку собственного аккаунта, в том числе передав UUID в другом регистре (409). Отсутствующий пользователь — 404; неверные UUID/причина/поля — 400; без сессии — 401, без роли или с неверным Origin — 403.

Блокировка атомарно переводит пользователя в BLOCKED, удаляет все его сессии и отменяет активные участия в будущих не начатых поездках. Для водителя отменяются его DRAFT/PUBLISHED с departureAt позже серверного времени и пустыми startedAt/completedAt, вместе со всеми PENDING/CONFIRMED-заявками. Для пассажира отменяются только его PENDING/CONFIRMED в таких поездках; остальные пассажиры и сама чужая поездка сохраняются. При двух ролях применяются оба правила. PENDING-платежи отменяются без списания, SUCCEEDED полностью возвращаются в демо-режиме. Некорректный платёж даёт 409 с откатом всей блокировки. Прошедшие, начатые, завершённые и ранее отменённые поездки и их история не изменяются.

Разблокировка переводит пользователя в ACTIVE. Старые сессии, отменённые поездки, заявки и платежи не восстанавливаются: нужен новый вход. Повтор уже установленного статуса возвращает changed=false и нулевые счётчики без новых событий; новая причина при таком повторе не заменяет причину предыдущего перехода.

Ответ 200 `{ id, status, changed, cancelledRides, cancelledBookings, revokedSessions }`, Cache-Control: no-store. Счётчики относятся только к этому запросу. В одной транзакции сохраняются user.blocked/user.unblocked с автором и причиной, события отменённых поездок/заявок и история демо-платежей. Участники получают уведомления об административной отмене/возврате, пользователь и администратор — SYSTEM о результате. Ошибка любой записи — безопасный 503 с полным откатом, включая сессии.

Команды поездок/бронирований и создание сессии при входе повторно проверяют ACTIVE под блокировкой строки пользователя. Поэтому запрос, успевший пройти проверку сессии до блокировки, не создаст новое активное участие после её завершения. Гонка со стартом либо оставляет уже начатую поездку, либо отменяет будущую с возвратом. Административные переходы сериализованы; взаимная одновременная блокировка двух администраторов не блокирует обоих. Интерфейс управления доступен администратору по #/admin/users (04.3).

## Модерация отзывов через API — 04.4

GET `/admin/reviews` доступен только активному ADMIN. Возвращает `{ items, total, page, pageSize }`, включая скрытые отзывы. Параметры: q (текст отзыва, причина скрытия и имена), hidden=true/false, recipientRole=DRIVER/PASSENGER, ratingMin/ratingMax, dateFrom/dateTo (ISO с часовым поясом, включительно), authorId, recipientId, bookingId, sort=newest/oldest, page и pageSize. Все условия объединяются через И; UUID, оценки 1–5 и диапазоны проверяются, неизвестные параметры запрещены. `%` и `_` в q ищутся буквально. При совпадении времени сортировка использует UUID; items и total читаются в RepeatableRead.

Элемент списка содержит id, bookingId, authorId, recipientId, rating, comment, createdAt, hiddenAt, hiddenReason, author/recipient `{ id, fullName }`, recipientRole, bookingStatus и rideStatus. Контакты, пароли и сессии не выдаются. Администратор видит также исторически некорректные участия; при неверной паре участников recipientRole=null, такие записи не учитываются в публичном рейтинге.

POST `/admin/reviews/:id/hide` и `/admin/reviews/:id/restore` требуют ADMIN, разрешённый Origin и тело `{ "reason": "Причина решения" }`. Причина обязательна для обеих команд, 1–500 символов после trim. Скрытие устанавливает hiddenAt/hiddenReason; восстановление очищает их, сохраняя причину в аудите. Ответ 200 `{ id, hiddenAt, hiddenReason, changed }`. Повтор текущего состояния возвращает changed=false, сохраняет первую причину/дату и не создаёт новых записей.

Переход, ActivityLog review.hidden/review.restored с администратором и причиной и SYSTEM-уведомления автору, получателю и администратору сохраняются в одной транзакции. Один пользователь получает не более одного уведомления на переход. В журнале сохраняются bookingId, участники и прежняя/новая дата скрытия без копии текста отзыва. Скрытый отзыв сразу исключается из собственных/публичных списков, раздельных рейтингов и рейтинга публичной карточки водителя. После восстановления снова учитывается только корректное завершённое участие; повторная оценка автором по-прежнему запрещена.

Без сессии/при блокировке — 401, без ADMIN/с неверным Origin — 403, отсутствующий отзыв — 404, неверные параметры/причина — 400. Сбой чтения или записи — безопасный 503, мутация полностью откатывается вместе с уведомлениями и аудитом. Все ответы имеют Cache-Control: no-store. Интерфейс модерации доступен администратору в 04.5.

## История собственных действий администратора — 04.5

GET `/admin/activity` требует сессию ADMIN и возвращает только записи текущего автора. actorId из запроса не принимается. В историю входят user.blocked/unblocked, review.hidden/restored и связанные ride.cancelled, booking.cancelled, payment.cancelled/refunded. Параметры q (причина, код действия, тип/UUID объекта), action, resourceType=user/review/ride/booking/payment, resourceId (UUID), dateFrom/dateTo, sort=newest/oldest, page и pageSize. Фильтры объединяются через И, даты включительны; диапазоны, UUID и неизвестные поля проверяются.

Ответ `{ items, total, page, pageSize }`, элемент `{ id, action, resourceType, resourceId, reason, createdAt }`. Возвращается только reason из JSON details, без произвольных данных журнала, контактов или секретов. Причина может быть null у записи демо-платежа; основное решение хранится отдельной записью. Список и total читаются в RepeatableRead со стабильной сортировкой по времени/UUID; Cache-Control: no-store. Ошибки: 400 неверные параметры, 401 нет сессии, 403 нет ADMIN, 503 безопасная ошибка чтения.

Экран модерации доступен по #/admin/reviews, история — #/admin/activity. Подтверждение модерации администратору в уведомлениях ведёт на экран модерации; автор и получатель переходят в собственные отзывы.

# CampusRide

Учебный сервис совместных поездок студентов и сотрудников **УрФУ, Екатеринбург**. Дата защиты — **9 ноября 2026 года**.

Водитель публикует поездку, пассажир находит её и бронирует места, водитель подтверждает заявку. После завершения участники оставляют двусторонние отзывы. Отмена, оплата и возврат демонстрационные; реальные деньги не используются. Интерактивная карта в первую версию не входит.

## Состояние проекта

Сервис разрабатывается поэтапно. Сейчас доступны:

- Bun-монорепозиторий: Vite/React, NestJS API и общий пакет UI.
- Пресет shadcn `b1tgce4mm`: Base UI, Luma, Inter, Tailwind CSS, pointer на кнопках.
- Поиск поездок с фильтрами, сортировкой, пагинацией и публичной карточкой; запросы через Vite-прокси `/api`.
- API создания заявки пассажиром с резервированием мест и защитой от повторной отправки; подтверждение и отклонение водителем.
- API двусторонних отзывов по завершённым заявкам с проверкой участников и защитой от повторной оценки.
- Проверки состояния API и подключения к PostgreSQL, Swagger/OpenAPI.
- API регистрации пассажира, входа и выхода, семидневные cookie-сессии и текущий пользователь (`/api/auth/me`).
- Prisma-схема из 17 сущностей, SQL-миграции и ER-диаграмма.
- Конфигурация PostgreSQL, Docker Compose и GitHub Actions.
- Форматирование, линтинг, проверка типов, сборка и HTTP-тесты авторизации с настоящим PostgreSQL.

**Ещё не реализованы:** полные кабинеты пассажира и администратора, статистика и модерация. Водителю доступны профиль, автомобили, черновики, публикация, отмена, старт и завершение поездок. Вход и регистрация работают через интерфейс с серверными сессиями.

Полный Compose-стек проверен: API и прокси фронтенда соединяются с PostgreSQL. SQL-проверки ограничений выполняются на настоящей БД с откатом тестовых записей. HTTP-тесты состояния используют подмену клиента, а тесты регистрации и сессий — настоящую БД; они создают аккаунты на уникальных доменах `*.campusride.test` и удаляют только свои записи после тестов. CI применяет миграции до запуска HTTP-тестов.

## Стек

Bun 1.4, TypeScript, React/Vite, Tailwind CSS, shadcn/ui (Base UI), NestJS, Prisma ORM 7.10.1, PostgreSQL 17, Docker Compose. Задачи workspaces запускаются через Turborepo. Версии зафиксированы в `bun.lock`; не создавайте параллельные lockfile других менеджеров пакетов.

## Локальная разработка

Понадобятся Bun 1.4.0, Node.js 24+ для инструментов сборки и Docker с Compose для PostgreSQL. Альтернатива Docker — собственный PostgreSQL 17 с URL в `.env`.

Из корня репозитория:

```sh
cp .env.example .env
bun install --frozen-lockfile
bun run db:up
bun run db:generate
bun run db:deploy
bun run dev
```

`db:deploy` применяет существующую начальную миграцию. Запуск `dev` поднимает Vite и NestJS с отслеживанием изменений. Пароли в `.env.example` предназначены только для локальной демонстрации, файл `.env` исключён из Git.

Адреса:

- Интерфейс: <http://localhost:5173>.
- API: <http://localhost:3001/api>.
- Swagger: <http://localhost:3001/api/docs>.
- OpenAPI JSON: <http://localhost:3001/api/docs-json>.

На главной странице кнопка «Проверить подключение» отправляет `GET /api/health`. Запрос виден в DevTools → Network. Кнопка «Документация API» открывает Swagger через тот же прокси.

### Если PostgreSQL пока недоступен

После копирования `.env`, установки зависимостей и генерации клиента можно выполнить `bun run dev` для работы с каркасом. `/api/health` будет доступен, а `/api/health/ready` вернёт `503`. Это ожидаемо без БД; будущие функции предметной области потребуют PostgreSQL и миграций.

## Регистрация через API

Откройте Swagger **через фронтенд**: <http://localhost:5173/api/docs>. Выполните `POST /api/auth/register`, затем `GET /api/auth/me`: браузер сохранит `HttpOnly` cookie автоматически. Используйте новый email, имя от 2 до 100 символов и пароль от 10 до 128 символов. Необязательное поле `affiliation` — до 200 символов. Регистрация назначает только `PASSENGER`; поля ролей, статуса и идентификатора от клиента отклоняются.

Пример из терминала (cookie-файл храните вне репозитория):

```sh
curl -i -c /tmp/campusride.cookies http://localhost:5173/api/auth/register \
  -H 'Content-Type: application/json' \
  -H 'Origin: http://localhost:5173' \
  --data '{"email":"anna@campusride.test","password":"CampusRide-demo-2026","fullName":"Анна Соколова"}'
curl -b /tmp/campusride.cookies http://localhost:5173/api/auth/me
```

Успешная регистрация возвращает `201` и безопасные данные пользователя, повторный email — `409`, неверные/лишние поля — `400`. Неподходящий или отсутствующий `Origin` даёт `403`: значение должно точно совпадать с `WEB_ORIGIN`. Поэтому интерактивную регистрацию в Swagger выполняйте через порт фронтенда `5173`, а не напрямую через `3001`.

Сессия действует 7 дней; в БД хранится SHA-256-хеш случайного 256-битного токена. Cookie имеет `HttpOnly`, `SameSite=Lax`, `Path=/`, а при `NODE_ENV=production` — `Secure` (требует HTTPS). Истёкшая, удалённая сессия или заблокированный пользователь получают `401`. Ответы с данными пользователя не кэшируются.

Регистрация ограничена десятью попытками в минуту с одного IP, включая неверные формы. Лимит хранится в памяти одного API-процесса и сбрасывается при его перезапуске. За локальным Vite-прокси клиенты могут иметь один IP; недоверенные `X-Forwarded-For` не используются для обхода лимита. Для нескольких серверных процессов потребуется общее хранилище лимитов.

## Docker на macOS через Colima

Для Apple Silicon проверена установка Docker CLI, Compose, Buildx и Colima через Homebrew ([инструкция Colima](https://colima.run/docs/installation/)):

```sh
brew install colima docker docker-compose docker-buildx
mkdir -p "$HOME/.docker/cli-plugins"
ln -s "$(brew --prefix docker-compose)/bin/docker-compose" "$HOME/.docker/cli-plugins/docker-compose"
ln -s "$(brew --prefix docker-buildx)/bin/docker-buildx" "$HOME/.docker/cli-plugins/docker-buildx"
colima start campusride --cpus 4 --memory 4 --disk 24 --vm-type vz --mount-type virtiofs --runtime docker
docker compose version
```

Если плагины уже настроены, повторно создавать ссылки не нужно. Профиль `campusride` использует 4 ГБ памяти; активный Docker context — `colima-campusride`. После перезагрузки VM запускается командой `colima start campusride`. Остановка — `colima stop campusride`; данные сохраняются. Автозапуск при входе в систему не настраивается.

Не запускайте локальные Vite/NestJS и их контейнеры одновременно на одинаковых портах. Для перехода к локальной разработке оставьте БД, остановив только приложения:

```sh
docker compose stop api web
bun run dev
```

Для возврата в контейнерный режим сначала остановите `bun run dev`, затем выполните `docker compose up -d`.

## Полный запуск в Docker

Для этого варианта Bun и Node.js на хосте не нужны — достаточно Docker с Compose:

```sh
cp .env.example .env
docker compose up --build -d
```

Compose поднимает PostgreSQL, применяет миграции при запуске API, ждёт готовности API и запускает собранный фронтенд. Адреса остаются теми же. Используется Vite preview для учебной локальной демонстрации; промышленное развёртывание потребует отдельной конфигурации.

```sh
docker compose logs -f api web
docker compose down
```

Обычный `down` сохраняет данные в именованном томе. Удаление тома уничтожает данные; не добавляйте `-v`, если их нужно сохранить.

## Команды

Все команды выполняются из корня:

```sh
bun run dev              # Оба приложения с отслеживанием изменений
bun run dev:web          # Только фронтенд
bun run dev:api          # Только API
bun run build            # Сборка фронтенда и API
bun run start:api        # Запуск уже собранного API
bun run check            # Генерация Prisma, схема, формат, линтеры, типы, тесты, сборка
bun run format           # Автоформатирование
bun run format:check     # Проверка форматирования
bun run lint             # ESLint / Oxlint
bun run typecheck        # TypeScript
bun run test             # HTTP-тесты; PostgreSQL и миграции обязательны
bun run db:test          # Ограничения в PostgreSQL из Compose; данные откатываются
bun run db:validate      # Проверка Prisma-схемы
bun run db:generate      # Генерация Prisma Client
bun run db:deploy        # Применение существующих миграций
bun run db:migrate --name change_name  # Создание новой миграции в разработке
bun run db:studio        # Просмотр БД через Prisma Studio
bun run db:up            # Только PostgreSQL в Docker
bun run db:down          # Остановка PostgreSQL без удаления данных
```

Для отдельных `typecheck` и `test` на чистой установке сначала выполните `bun run db:generate`. Команда `check` делает это сама. Для `test` и `check` предварительно запустите PostgreSQL и примените миграции (`bun run db:up`, `bun run db:deploy`). Prisma Client генерируется также перед сборкой и запуском API в разработке.

Изменения БД проводятся миграциями. Не заменяйте их `prisma db push`: частичные индексы и дополнительные SQL-ограничения описаны в миграции, а не полностью в Prisma-схеме.

## Демо и время

Проект рассчитан на пассажира, водителя и администратора; первые две роли можно совмещать. Доступны навигация кабинетов по ролям и редактирование профиля; предметные разделы будут добавлены отдельными этапами. Демо-аккаунты перечислены ниже.

Предметные даты используют **Asia/Yekaterinburg (UTC+5)**, данные в PostgreSQL хранятся в UTC. Будущее наполнение должно формировать поездки относительно даты запуска, чтобы сценарий оставался рабочим к защите.

## Работа с репозиторием

Спецификации и сообщения коммитов пишутся на русском. Коммиты создаются только по прямому указанию владельца. Файлы `AGENTS.md` и каталог `.agents/` не используются.

### Вход и выход через API

`POST /api/auth/login` принимает `{ email, password }`, возвращает `200` с безопасными данными пользователя и устанавливает новую семидневную cookie. Email нормализуется, пароль передаётся без обрезки пробелов. Неверный пароль, неизвестный email и заблокированный аккаунт дают одинаковый ответ `401`; неверные/лишние поля — `400`. Вход ограничен 10 попытками с IP за 60 секунд, независимо от регистрации; лимит учитывает невалидные формы.

`POST /api/auth/logout` удаляет текущую сессию и очищает cookie, возвращая `204`. Повторный выход, отсутствие или истечение сессии тоже дают `204`; сессии на других устройствах сохраняются. Оба запроса требуют разрешённый `Origin`; Swagger следует открывать через <http://localhost:5173/api/docs>. Интерфейс авторизации доступен на главной странице.

### Авторизация на сайте

Откройте <http://localhost:5173>. Выберите «Зарегистрироваться», укажите имя, email и пароль длиной 10–128 символов. После создания аккаунта вы авторизованы как пассажир. Кнопка «Выйти» завершает текущую сессию; повторный вход — по email и паролю. После перезагрузки сайт восстанавливает пользователя через `/api/auth/me`. Пароли и токены не сохраняются в localStorage. При ошибках API показывается сообщение, при сбое проверки сессии можно повторить запрос. Демо-аккаунты перечислены ниже.

Клиентские тесты форм и восстановления сессии запускаются через `bun run --filter @campusride/web test` и входят в `bun run check`. Они подменяют fetch; серверные HTTP-тесты отдельно проверяют настоящую БД.

### Демо-аккаунты

После запуска PostgreSQL и применения миграций выполните `bun run db:seed` из корня проекта. Для полностью контейнерного запуска после сборки образа: `docker compose exec api bun run db:seed`. Seed запускается вручную, не при каждом старте приложения.

| Email                     | Пароль               | Роли               |
| ------------------------- | -------------------- | ------------------ |
| passenger@campusride.test | CampusRide-demo-2026 | Пассажир           |
| driver@campusride.test    | CampusRide-demo-2026 | Пассажир, водитель |
| admin@campusride.test     | CampusRide-demo-2026 | Администратор      |

Введите эти данные в форму входа на <http://localhost:5173>. Это публичные учебные аккаунты для локальной демонстрации; не создавайте их в публичном рабочем развёртывании. Подключение водителя с первым автомобилем доступно пассажиру; API и экран управления автомобилями готовы; поездки добавляются следующими этапами.

Повторный seed не сбрасывает пароли, имена, статусы, роли или сессии существующих пользователей. При совпадении email существующий аккаунт сохраняется целиком, даже если его пароль и роли отличаются от таблицы; seed не выдаёт ему дополнительные права. Три аккаунта создаются в одной транзакции, пароли хешируются Argon2id, сессии создаются только при входе. Публичная регистрация по-прежнему назначает только роль пассажира.

### Личный кабинет и профиль

После входа откроется кабинет доступной роли. В меню отображаются кабинеты пассажира, водителя и администратора в соответствии с ролями аккаунта; при совмещении ролей доступны оба кабинета. Общий раздел «Мой профиль» позволяет изменить имя, телефон и принадлежность к университету. Email доступен только для чтения. Пустые телефон и принадлежность очищают значения. После сохранения имя обновляется в шапке.

Прямая ссылка на профиль — <http://localhost:5173/#/profile>. Навигация использует hash-ссылки и сохраняет выбранный раздел при перезагрузке. Ошибку загрузки можно повторить, ошибка сохранения сохраняет введённые значения; при истечении сессии сайт предлагает войти снова. Разделы поездок и модерации пока помечены как находящиеся в разработке. Видимость пунктов меню не заменяет серверные проверки прав.

### Стать водителем

Войдите как пассажир и выберите «Стать водителем» в меню (прямая ссылка: <http://localhost:5173/#/become-driver>). Описание необязательно; укажите марку, модель, цвет, госномер и количество пассажирских мест от 1 до 8. Поддерживается стандартный номер легкового автомобиля РФ вида А123ВС196; кириллица и латиница нормализуются сервером.

После успешной отправки профиль водителя и первый автомобиль сохранены, в меню появляется кабинет водителя, кабинет пассажира остаётся доступен. При ошибке формы введённые данные сохраняются. Повторный запрос и занятый номер возвращают конфликт без создания лишнего автомобиля. Добавление и редактирование остальных автомобилей доступны в разделе «Мои автомобили». Демо-аккаунт водителя уже имеет роль и не использует форму подключения; первый автомобиль можно добавить в разделе «Мои автомобили», недостающий профиль создастся автоматически.

### API автомобилей

В Swagger доступны `GET /api/me/vehicles`, `POST /api/me/vehicles` и `PATCH /api/me/vehicles/:id`. Войдите как водитель; мутации требуют Origin, поэтому открывайте Swagger через <http://localhost:5173/api/docs>. Список поддерживает `q`, фильтры `make`, `model`, `color`, `minSeats`/`maxSeats` и пагинацию `page`/`pageSize`. Возвращаются только свои автомобили.

Для добавления передайте `{ "make": "Kia", "model": "Rio", "color": "Белый", "registrationNumber": "А123ВС196", "passengerSeats": 3 }`. Для изменения укажите UUID своего автомобиля и только изменяемые поля. Номер должен быть уникальным; попытка изменить чужой автомобиль даёт `404`. Владельца клиент не задаёт. Экран автомобилей доступен по ссылке <http://localhost:5173/#/vehicles>.

### Мои автомобили

Войдите как водитель и откройте «Мои автомобили» в меню. Кнопка «Добавить автомобиль» открывает форму марки, модели, цвета, госномера и числа пассажирских мест. Кнопка «Редактировать» заполняет форму данными выбранного автомобиля; «Отмена» закрывает её без сохранения. При ошибке поля сохраняются, во время запроса повторная отправка блокируется. Успешное сохранение обновляет список из API. После добавления поиск и фильтры сбрасываются; после редактирования текущие условия сохраняются.

Поиск работает по марке, модели, цвету и госномеру; фильтры — марка, модель, цвет и минимум пассажирских мест. Нажмите «Найти» для применения или «Сбросить фильтры» для очистки. Список разбит на страницы по 10 автомобилей. Пустой список отличается от отсутствия результатов поиска; при сбое доступна повторная загрузка. Раздел виден только водителям, сервер дополнительно проверяет роль и владельца.

### Справочники маршрутов

`bun run db:seed` теперь также готовит пять районов/микрорайонов Екатеринбурга, три корпуса УрФУ и семь точек маршрутов. Повторный запуск сохраняет существующие UUID и изменённые данные. Источники адресов и правила подготовки описаны в [документации демо-данных](docs/demo-data.md).

Доступны публичные `GET /api/districts`, `GET /api/campuses`, `GET /api/locations`. Каждый список поддерживает поиск, четыре фильтра и пагинацию; контракт опубликован в Swagger. Например, `/api/locations?kind=CAMPUS&address=Мира&pageSize=10` возвращает точки корпусов по указанному адресу. Форма создания поездки доступна водителю по ссылке <http://localhost:5173/#/rides/new>.

### Создать черновик поездки через API

В Swagger доступен `POST /api/rides` для роли водителя. Открывайте <http://localhost:5173/api/docs>, войдите как водитель, возьмите UUID своего автомобиля из `/api/me/vehicles` и точки из `/api/locations`. Передайте автомобиль, разные начальную и конечную точки, будущее `departureAt` с часовым поясом, `seatsTotal`, цену `priceKopecks` в целых копейках и непустые условия `conditions` с уточнением места встречи. Максимум мест — 8 и не больше вместимости автомобиля; цена может быть нулевой.

Необязательные параметры: `musicAllowed` (по умолчанию true), `luggageAllowed` и `smokingAllowed` (false), до 10 остановок `stops: [{ locationId }]` без повторов. Сервер создаёт `DRAFT` и назначает автора из сессии. Ответ возвращает созданный черновик, время в UTC и порядок остановок. Ошибки откатывают создание. Создание и редактирование черновиков доступны через API и форму; публикация доступна через API и экран своих поездок.

### Управление своими черновиками через API

Водителю доступны `GET /api/me/rides` (свой список) и `GET /api/me/rides/:id` (свои детали), `PATCH /api/rides/:id` (изменить черновик) и `DELETE /api/rides/:id` (удалить). Мутации требуют Origin; используйте Swagger через фронтенд. Статус, автор и служебные поля не принимаются. Изменять и удалять можно только `DRAFT` без бронирований; чужие и отсутствующие поездки дают одинаковый `404`.

PATCH сохраняет пропущенные поля и повторно проверяет автомобиль, маршрут, вместимость и будущее время. `stops` заменяет список остановок целиком; `[]` очищает его. Список поддерживает `q`, статус, автомобиль, конечные точки, максимум цены, минимум предложенных мест, временные границы с часовым поясом, сортировку и пагинацию. Полный контракт — в [документации API](docs/api.md). Форма создания и редактирования доступна; экран списка и публикация доступны в разделе «Мои поездки».

### Форма поездки

Войдите как водитель и выберите «Создать поездку» (<http://localhost:5173/#/rides/new>). Автомобили и точки маршрута загружаются из API, включая следующие страницы справочников. Если автомобиля нет, форма предложит добавить его в разделе «Мои автомобили».

Выберите автомобиль и разные точки отправления/назначения, при необходимости добавьте до десяти остановок и измените их порядок. Укажите будущее время по Екатеринбургу (UTC+5): часовой пояс устройства не влияет на введённое значение. Цена вводится в рублях с точкой или запятой, максимум два десятичных знака; в API передаются целые копейки. Укажите места в пределах вместимости, настройки музыки/багажа/курения и уточнение места встречи.

После сохранения появится подтверждение со ссылкой «Редактировать черновик». Существующий черновик также можно открыть из списка «Мои поездки» или по hash-маршруту `#/rides/<UUID>/edit`. Для редактирования загружается собственная поездка, настройки и порядок остановок сохраняются. Опубликованные и другие нечерновые статусы не открывают форму. Ошибки API сохраняют введённые значения, повторная отправка блокируется на время запроса, истёкшая сессия возвращает форму входа. Для публикации откройте «Мои поездки» и подтвердите действие у нужного черновика.

### Опубликовать черновик через API

Водитель вызывает `POST /api/rides/<UUID>/publish` без тела или с `{}` через Swagger с разрешённым Origin. Сервер повторно проверяет условия и переводит свой `DRAFT` в `PUBLISHED`. Ответ — `200` с поездкой. Одновременно сохраняются событие статуса и системное уведомление водителю; уведомление доступно в разделе «Уведомления».

Повторный запрос к `PUBLISHED` возвращает актуальную поездку без повторных записей, включая параллельные вызовы. Истёкшее отправление, уменьшившаяся вместимость и незаполненные условия блокируют первую публикацию; чужая поездка скрывается за `404`. Сбой события или уведомления откатывает статус. После публикации API черновиков запрещает редактирование и удаление. Экран списка и кнопка публикации доступны в разделе «Мои поездки».

### Мои поездки и публикация

Откройте «Мои поездки» в меню водителя (<http://localhost:5173/#/rides>). Список показывает маршрут, время Екатеринбурга, автомобиль, цену в рублях, предложенные места, условия, остановки и статус. Поиск работает по условиям, конечным точкам и автомобилю. Фильтры — статус, автомобиль, начальная и конечная точки, максимум цены, минимум предложенных мест и диапазон отправления. Для временных границ допустимы прошлые даты: список включает историю. Есть сортировка, сброс фильтров и страницы по 10 записей.

У черновика доступны редактирование, публикация и удаление. Публикация и удаление выполняются только после подтверждения, затем список перечитывается с сохранением текущих фильтров. У опубликованной поездки действия черновика скрыты; API также запрещает их. После создания или редактирования формы ссылка «Открыть мои поездки» ведёт к списку. Пустой список отличается от отсутствия совпадений; загрузку после ошибки можно повторить.

Проверен полный сценарий через интерфейс с настоящим API и PostgreSQL: создать → отредактировать → открыть список → подтвердить публикацию. Статус меняется без перезагрузки; повтор публикации оставляет ровно одно событие и уведомление. Временные записи проверки удалены. Форма публичного поиска, карточки результатов и экран деталей доступны.

### Публичный поиск поездок — API

Доступен `GET /api/rides` без входа. Например: `/api/rides?direction=TO_CAMPUS&date=2026-11-09&timeFrom=08:00&timeTo=09:00&maxPriceKopecks=20000&minSeats=2`. Дата и часы — Екатеринбург. Дополнительные фильтры: район отправления, корпус и условия; есть поиск `q`, сортировка и пагинация. Полный контракт опубликован в Swagger и [документации API](docs/api.md).

Выдаются только опубликованные будущие поездки активных водителей с ролью DRIVER. Ответ не содержит контактов, госномеров и данных сессии. Поле availableSeats показывает свободный остаток после вычета мест PENDING/CONFIRMED; minSeats фильтрует по нему, заполненные поездки исключаются. API карточки, форма поиска, карточки результатов и экран деталей доступны.

### Свободные места в публичном поиске

GET `/api/rides` возвращает и `seatsTotal` (предложено), и `availableSeats` (свободно). Из предложенных мест вычитается сумма мест бронирований PENDING и CONFIRMED. Отменённые, отклонённые и завершённые заявки не учитываются. Например: 3 предложенных места − 1 ожидающее − 1 подтверждённое = 1 свободное.

`minSeats=2` покажет только поездки как минимум с двумя свободными местами. Заполненные поездки исключаются и без этого параметра. Фильтр работает до пагинации, поэтому total и страницы отражают доступные поездки. Расчёт выполняется в БД; публичный ответ не раскрывает заявки и пассажиров. Поиск не резервирует место: резерв создаётся отдельным POST /rides/:id/bookings.

### Публичная карточка — API

GET `/api/rides/<UUID>` возвращает доступную будущую опубликованную поездку: маршрут с адресами, остановки по порядку, цену, условия, предложенные и свободные места, описание автомобиля и публичный профиль водителя. У профиля есть описание, рейтинг и количество видимых отзывов пассажиров завершённых поездок. Без отзывов рейтинг — null, количество — 0. Рейтинг в роли пассажира не смешивается с рейтингом водителя.

Неизвестная, черновая, прошедшая, заполненная поездка или недоступный водитель дают одинаковый 404. Контакты, госномер, данные аккаунта и заявок не раскрываются. Карточка и поиск используют один расчёт доступности. Экран карточки доступен по ссылке «Подробнее» из поиска; создание отзывов добавляется отдельным этапом. Подробный контракт — в Swagger и [документации API](docs/api.md).

### Форма публичного поиска

Выберите «Найти поездку» в верхнем меню или откройте <http://localhost:5173/#/search>. Вход не требуется; поиск доступен и из аккаунтов всех ролей. Районы отправления и корпуса загружаются из API. Можно выбрать направление, дату и время Екатеринбурга, район, корпус, максимум цены, число свободных мест, музыку, багаж, курение и поисковый текст.

«Найти поездки» сохраняет применённые условия в hash-параметрах ссылки и выполняет настоящий GET /api/rides. Ссылка восстанавливает форму после перезагрузки и переходов назад/вперёд; цена из целых копеек отображается в рублях, условия false и нулевая цена сохраняются. Новая отправка сбрасывает страницу на первую, «Сбросить условия» очищает форму и ссылку. Время требует дату; неверные диапазоны и цены проверяются до запроса.

Результаты показывают маршрут с адресами, время Екатеринбурга, цену за место, водителя, автомобиль, условия и свободный остаток мест. Есть четыре варианта сортировки и постраничная навигация; фильтры сохраняются в ссылке, новая сортировка или отправка формы возвращает на первую страницу. Пустой поиск и опустевшая страница различаются; для сбоев справочников и поиска предусмотрен повтор запроса. Ссылка «Подробнее» открывает публичную карточку с полным маршрутом и остановками, условиями, автомобилем, описанием водителя и его рейтингом. Вход не требуется. «Вернуться к результатам» восстанавливает применённые фильтры, сортировку и страницу поиска. Прямая ссылка `#/ride/<UUID>` также работает; без параметров поиска возврат ведёт к пустой форме. Недоступная поездка показывает отдельное сообщение, временные ошибки можно повторить. Бронирование доступно пассажиру прямо в карточке поездки.

### Создание заявки через API

В Swagger через фронтенд-прокси войдите пассажиром и вызовите `POST /api/rides/<UUID>/bookings` с телом `{ "seats": 1, "requestKey": "<новый UUID>" }` и Origin `http://localhost:5173`. Поездка должна быть опубликована, ещё не отправиться и иметь достаточно свободных мест. Ответ `201` содержит заявку `PENDING` и зафиксированную серверную цену в копейках. Места резервируются до решения водителя; вместе с заявкой создаётся ожидающий демонстрационный платёж.

При сетевом повторе отправьте тот же requestKey и число мест: ответ `200` вернёт ту же заявку без повторного резервирования. Для новой попытки после отмены или отклонения нужен новый ключ. Другая активная заявка, конфликт ключа или нехватка мест дают `409`. Собственную поездку бронировать нельзя. Параллельные запросы сериализуются блокировкой поездки, поэтому последние места не продаются дважды. Форма бронирования, списки заявок, решения водителя и уведомления доступны через интерфейс.

### Решение водителя через API

Войдите водителем соответствующей поездки. `POST /api/bookings/<UUID>/confirm` с пустым телом подтверждает ожидающую заявку; `POST /api/bookings/<UUID>/reject` с `{ "reason": "Изменился маршрут" }` отклоняет её. Оба запроса требуют разрешённый Origin и возвращают `200`. Причина обязательна: 1–500 символов после удаления пробелов по краям. Подтверждение сохраняет резерв мест, отклонение освобождает его. Ответ дополнен cancellationReason (причина отклонения или null).

Новое решение допустимо только для PENDING до отправления опубликованной поездки. Повтор того же решения не создаёт событие; для повторного отклонения причина должна совпадать. Противоположное решение, другой статус заявки или отправившаяся поездка дают `409`; чужая и отсутствующая заявка — одинаковый `404`. Уведомление пассажиру сохраняется атомарно с решением. Подтверждение выполняет демонстрационную оплату, отклонение отменяет ожидающий платёж. Реальные деньги не используются.

### Бронирование в карточке поездки

Откройте «Найти поездку» → «Подробнее». Войдите пассажиром, выберите число мест и нажмите «Забронировать места». Форма показывает итоговую стоимость; сервер повторно проверяет доступность и фиксирует цену. После отправки видны номер, количество мест, стоимость и статус заявки. Свободные места перечитываются из API. Успех сохраняется на экране даже при заполнении поездки или ошибке обновления остатка.

Гостю предлагается вход с возвратом к исходной карточке и сохранённому поиску. Для собственной поездки и аккаунта без роли PASSENGER отправка недоступна. Во время запроса кнопка блокируется. Если ответ потерялся или произошёл временный сбой, «Повторить отправку» использует прежний ключ и число мест в открытой форме. После конфликта мест форма обновляет остаток и разрешает скорректировать выбор. Сохранённые заявки доступны в личном кабинете; решения водителя доступны в разделе «Заявки пассажиров».

### Заявки пассажира

Войдите пассажиром и откройте «Мои заявки» в кабинете (<http://localhost:5173/#/bookings>) или перейдите туда после бронирования. Здесь видны маршрут и адреса, водитель, автомобиль, время Екатеринбурга, число мест, зафиксированная цена, сумма и статусы заявки и поездки. Причина отклонения сохраняется в истории. Данные собственных заявок остаются доступны и после закрытия поездки. Публичная карточка закрытой или заполненной поездки может быть недоступна.

Список поддерживает поиск по маршруту, водителю, автомобилю и причине, разделы «Все заявки», «Предстоящие поездки», «История», статусы заявки и поездки, минимум мест, максимум цены места и диапазон отправления. Есть сортировка, страницы по 10 записей, сброс и обновление для получения решения водителя. Предстоящими считаются PENDING/CONFIRMED будущей PUBLISHED-поездки; история содержит остальные заявки, включая отклонённые будущие. Фильтры хранятся в открытом разделе; после перезагрузки список заново читает все свои заявки из API.

### Заявки пассажиров у водителя

Войдите водителем и откройте «Заявки пассажиров» (<http://localhost:5173/#/ride-bookings>). Список показывает только заявки ваших поездок: имя и принадлежность пассажира к университету, маршрут, время, места, стоимость, статусы и текущий свободный остаток. Доступны поиск по пассажиру, маршруту, автомобилю и причине отказа, фильтры статусов, периода, числа мест, цены и дат, сортировка и пагинация.

У ожидающей заявки будущей опубликованной поездки выберите «Подтвердить» или «Отклонить». Перед отправкой подтвердите действие; при отклонении укажите причину. После успеха список и остаток мест загружаются заново с прежними фильтрами. При конфликте серверного состояния список также обновляется; при временном сбое можно повторить то же решение. Подтверждённую заявку отдельно отклонить нельзя. Уведомления участникам и демонстрационные платежи реализованы.

### Уведомления и демонстрация бронирования

Раздел «Уведомления» доступен в кабинете каждой роли (<http://localhost:5173/#/notifications>). Водитель получает уведомление о новой заявке, пассажир — о подтверждении или отклонении с причиной. Есть поиск, фильтры типа, прочтения, объекта и диапазона дат, страницы и обновление списка. Уведомления можно помечать прочитанными; ссылка открывает связанный раздел заявок. Доставка внутри сайта: обновите раздел или откройте его снова для получения новых событий.

Проверка сценария для защиты:

1. Войдите водителем, создайте поездку с будущим временем и опубликуйте её.
2. Войдите пассажиром, найдите поездку по направлению и времени, откройте карточку и забронируйте место. Проверьте PENDING в «Моих заявках».
3. Войдите водителем, откройте уведомление о заявке и перейдите к заявкам пассажиров. Подтвердите заявку.
4. Войдите пассажиром, откройте уведомление о подтверждении и «Мои заявки» → «Предстоящие поездки». Статус — CONFIRMED; повторного списания мест нет.
5. В DevTools → Network видны GET /rides, GET /rides/:id, POST /rides/:id/bookings, POST /bookings/:id/confirm, GET /notifications и GET /me/bookings.

Полный серверный проход проверяется HTTP-тестом с PostgreSQL; отдельный тест интерфейса проходит те же экраны со сменой ролей и подменённым транспортом. Ошибка записи уведомления откатывает заявку/решение и событие статуса; повтор команды не дублирует уведомления. Демонстрационные оплата, отмена и полный возврат реализованы; API старта доступно; ожидающие заявки обрабатываются при старте; API завершения доступно; старт и завершение доступны через интерфейс.

### Отмена, демонстрационные оплата и возврат

После создания заявки платёж имеет статус PENDING и сумму по зафиксированной цене всех забронированных мест. Подтверждение водителем автоматически переводит его в SUCCEEDED; отклонение — в CANCELLED без списания. Это исключительно имитация: банковские карты и платёжные сервисы не используются. Бесплатная поездка также получает успешный демо-платёж на нулевую сумму. Статус, сумма и даты видны в карточке результата бронирования и в списках заявок обеих ролей.

В «Моих заявках» пассажир может нажать «Отменить мою заявку» для PENDING/CONFIRMED до отправления опубликованной поездки. После подтверждения действия места освобождаются; ожидающий платёж отменяется, успешный полностью возвращается (REFUNDED). Причина необязательна. Возврат всегда на всю сумму; повтор отмены не меняет дату или причину и не создаёт второе событие возврата.

В «Моих поездках» водитель может отменить DRAFT/PUBLISHED с обязательной причиной. Все активные заявки отменяются, успешные демо-платежи полностью возвращаются, остальные отменяются без списания. Обычная отмена начатой/завершённой поездки недоступна. Водитель может отменить просроченную PUBLISHED, если поездка ещё не начата. Участники получают уведомления, переходы и операции записываются в историю. Повтор отмены поездки требует прежнюю причину.

Перед запуском после обновления выполните `bun run db:deploy` и `bun run db:generate`. Новая миграция сохраняет существующие платежи и заполняет недостающие для прежних заявок без повторных уведомлений. Сумма в PostgreSQL хранится как bigint, в JSON — целое число копеек; поддерживаются восемь мест по максимальной цене без переполнения. Автоматические проверки покрывают возврат, нулевые суммы, права, повторы, конкурентные команды и откат всей поездки при ошибке одного платежа или уведомления.

### Ручной старт поездки через API — 02.1–02.2

Войдите водителем и вызовите в Swagger через фронтенд-прокси `POST /api/rides/<UUID>/start` с разрешённым Origin, без тела или с `{}`. Только собственная PUBLISHED-поездка: ответ `200` содержит `{ id, status: "IN_PROGRESS", startedAt }`. Время назначается сервером, состояние и событие статуса сохраняются атомарно. Ручной старт допускается как до запланированного отправления, так и после него. Поле startedAt также доступно в своих GET /me/rides и /me/rides/:id.

Повтор IN_PROGRESS возвращает прежнее время без нового события. После старта поездка исчезает из публичного поиска и карточки, новые заявки и обычная отмена недоступны. Подтверждённые бронирования и их демо-платежи сохраняются. При старте все PENDING атомарно переходят в REJECTED с причиной «Поездка началась без подтверждения заявки водителем.», их неоплаченные демо-платежи — в CANCELLED без списания. Резерв освобождается; история отклонённых и отменённых заявок сохраняется. Ошибка обработки любой заявки или уведомления о платеже откатывает весь старт, включая ранее обработанные заявки. Повтор не дублирует события и отмены платежей. Кнопки управления доступны в «Моих поездках»; уведомления о старте доступны водителю и подтверждённым пассажирам.

Обработка при старте сериализована с бронированием, подтверждением и отменой через общую блокировку поездки. Если новая заявка успела создаться первой, старт отклонит её; если старт завершился первым, новая заявка получит 404. Повтор исходного requestKey возвращает актуальный REJECTED/CANCELLED без нового резерва. Общий механизм платежей сохраняет PAYMENT_UPDATED и историю отмены платежа; уведомления о старте и автоотклонении сохраняются в той же транзакции.

### Завершение поездки через API — 02.3

Водитель вызывает `POST /api/rides/<UUID>/complete` в Swagger через фронтенд-прокси с разрешённым Origin, без тела или с `{}`. Доступно только для собственной IN_PROGRESS-поездки с корректным startedAt. Ответ `200`: `{ id, status: "COMPLETED", startedAt, completedAt }`. Время завершения назначает сервер; completedAt также доступно в своих GET /me/rides и /me/rides/:id.

Все CONFIRMED-заявки этой поездки атомарно становятся COMPLETED с событиями статусов. Успешные демо-платежи, суммы и даты оплаты сохраняются; возврат при завершении не выполняется. Ранее отменённые и отклонённые заявки не меняются. Пассажир видит завершённую поездку в истории. Повтор сохраняет время и не создаёт повторных событий. Ошибка обработки любой заявки откатывает весь переход. Неожиданный PENDING, некорректный платёж или timestamps дают 409 без частичных изменений. Кнопки управления доступны в «Моих поездках»; уведомления о завершении доступны участникам в центре уведомлений.

### Старт и завершение через кабинет водителя — 02.4

Откройте «Мои поездки» (<http://localhost:5173/#/rides>). У опубликованной поездки доступно «Начать поездку», у начатой — «Завершить поездку». Панель подтверждения показывает маршрут и время, предупреждает об обработке ожидающих заявок при старте и сохранении демо-оплаты при завершении. До подтверждения запрос не отправляется. Ручной старт возможен и до запланированного времени отправления.

После успеха статус и фактические время начала/завершения перечитываются из API и показываются по Екатеринбургу. Применённые фильтры и страница сохраняются; если поездка больше не соответствует фильтру, она исчезнет из выдачи. Во время команды действия блокируются. Временная ошибка оставляет подтверждение открытым для идемпотентного повтора, 404/409 закрывает устаревшую команду и обновляет данные. Ошибка загрузки списка после успешного действия не требует повторной отправки команды.

### Уведомления жизненного цикла — 02.5

В разделе «Уведомления» водитель и подтверждённые пассажиры получают сообщения о начале и завершении поездки со ссылкой на свой список. Ожидающая заявка при старте получает отдельное уведомление об отклонении с причиной. Ранее отменённые и отклонённые заявки не получают уведомлений о начале/завершении. В ActivityLog записываются `ride.started`, `ride.completed`, `booking.rejected` и `booking.completed`. Сбой записи откатывает всю операцию; повторы не создают дублей.

### Проверка полного сценария — 02.6

[Сценарий демонстрации](docs/demo-lifecycle.md) описывает проход от создания и публикации поездки до истории пассажира, ожидаемые сетевые запросы, уведомления, повторы и ручную проверку мобильной версии. Единый HTTP-тест с PostgreSQL проверяет этот проход автоматически; в 03.6 он расширен до встречных отзывов и рейтингов.

### Создание отзывов через API — 03.1

После завершения поездки пассажир и водитель могут независимо вызвать `POST /api/bookings/<UUID>/reviews` с `{ "rating": 5, "comment": "Поездка прошла хорошо." }` через Swagger с разрешённым Origin и своей сессией. Автор и второй участник назначаются сервером. Оценка 1–5, непустой комментарий до 1000 символов; один отзыв от участника на заявку. Повтор даёт 409, чужая заявка — 404, незавершённая — 409. Ответ 201 содержит созданный отзыв. Формы, списки, уведомления и развитие рейтингов добавляются следующими этапами.

### Списки отзывов и рейтинги через API — 03.2

`GET /api/me/reviews?direction=received` возвращает собственные полученные отзывы, `direction=sent` — оставленные. `GET /api/users/<UUID>/reviews` доступен публично для активного пользователя; `GET /api/users/<UUID>/ratings` возвращает отдельные средние и число оценок как водителя и пассажира. Без оценок среднее равно null. Скрытые отзывы не показываются и не учитываются.

Списки поддерживают поиск q, фильтры recipientRole, ratingMin/ratingMax, dateFrom/dateTo, сортировку newest/oldest и пагинацию. Публичный ответ не содержит номера бронирования, контактов и полей модерации. Формы и экраны отзывов добавляются следующими этапами.

### Оценка водителя пассажиром — 03.3

Войдите пассажиром, откройте «Мои заявки», выберите «История». У завершённой заявки завершённой поездки нажмите «Оценить водителя», выберите 1–5 и напишите комментарий до 1000 символов. «Отправить отзыв» сохраняет оценку через API; карточка показывает принятый текст и время. Уже оставленный отзыв отображается при открытии истории, повторная форма не предлагается. При ошибке подключения текст сохраняется для повтора. Формы оценки пассажира и общий экран отзывов остаются следующими этапами.

### Оценка пассажиров водителем — 03.4

Войдите водителем, откройте «Заявки пассажиров», выберите «История». У завершённой заявки завершённой поездки нажмите «Оценить пассажира», выберите оценку 1–5 и напишите комментарий до 1000 символов. Каждая заявка имеет отдельный отзыв, поэтому пассажиров одной поездки можно оценить независимо. Сохранённая оценка отображается при повторном открытии; при ошибке подключения ввод сохраняется. Получателя назначает сервер по заявке. Общий экран отзывов и уведомления добавляются следующими этапами.

### Отзывы, рейтинги и уведомления — 03.5

В кабинете откройте «Отзывы и рейтинги»: доступны полученные и оставленные отзывы, поиск по тексту/именам, роль получателя, диапазон оценки и дат, сортировка и страницы. Рейтинги как водителя и пассажира считаются отдельно по всем полученным оценкам, независимо от фильтров. В карточке публичной поездки показан рейтинг водителя и число отзывов.

Получателю нового отзыва приходит уведомление со ссылкой на этот раздел. Отзыв, уведомление и запись `review.created` в журнале сохраняются атомарно; ошибка откатывает всё, повтор не создаёт дублей. Скрытые отзывы не отображаются и не учитываются в рейтинге.

### Проверка встречных отзывов — 03.6

[Сценарий демонстрации](docs/demo-lifecycle.md) расширен до встречных отзывов и раздельных рейтингов. Единый HTTP-тест с PostgreSQL проверяет полный проход от создания поездки, обновление рейтинга в публичной карточке водителя, уведомления, журнал и запрет повторной/чужой оценки. Отдельный тест интерфейса проходит две сессии через формы, историю, уведомления и экран отзывов с подменой HTTP. Ручная проверка мобильной вёрстки и Network описана отдельно.

### Список пользователей администратора через API — 04.1

Войдите учебным администратором и вызовите `GET /api/admin/users` через Swagger. Доступны поиск q по имени/email, role, status, affiliation, registeredFrom/registeredTo, сортировка createdDesc/createdAsc/nameAsc и пагинация. Например: `/api/admin/users?role=DRIVER&status=ACTIVE&affiliation=УрФУ&page=1&pageSize=20`. В ответе — данные профиля, роли и даты, без паролей, сессий и телефона. Остальные роли получают 403, без сессии — 401. Управление блокировкой и экран списка добавляются следующими этапами.

### Блокировка пользователей через API — 04.2

Администратор может вызвать в Swagger с разрешённым Origin `POST /api/admin/users/<UUID>/block` или `/unblock` с `{ "reason": "Причина решения" }`. Причина обязательна, 1–500 символов. Самоблокировка запрещена. Блокировка завершает все сессии пользователя и отменяет активные участия в будущих не начатых поездках с демо-возвратами. У пользователя с обеими ролями обрабатываются поездки водителя и заявки пассажира. Начатые, завершённые и прошедшие поездки сохраняются.

Участники получают уведомления, решения записываются в журнал. Повтор текущего статуса не создаёт дублей. Разблокировка требует нового входа и не восстанавливает отменённые участия. Любая ошибка отмены, возврата или записи откатывает операцию целиком. Экран управления добавляется в 04.3.
